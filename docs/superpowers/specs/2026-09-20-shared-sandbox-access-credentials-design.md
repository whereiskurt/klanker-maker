# Shared sandbox access credentials — design

**Date:** 2026-09-20
**Status:** approved design, pre-implementation
**Scope:** `km vscode`, `km desktop`, `km herdr`, `km tunnel`, `km create`, `km destroy`, ttl-handler, `km doctor`

## 1. Problem

Every SSH-transport verb (`km vscode start`, `km herdr`, `km tunnel k8s|socks`) needs
the per-sandbox ed25519 private key at `~/.km/keys/<id>`, and `km desktop start` needs
the KasmVNC `user:pass` at `~/.km/desktop/<id>`. Both are generated by `km create` on
the laptop that ran it and exist nowhere else. Any other analyst who types `start` gets:

```
private key for <id> not found at ~/.km/keys/<id>. If you created this sandbox on a
different machine, copy the ~/.km/keys/<id>* files over
```

The only in-band recovery is `km vscode rekey` / `km desktop rekey`, which replaces the
box's `authorized_keys` (or `~/.kasmpasswd`) **wholesale** — it works for the person
who ran it and locks out whoever held the previous credential. With sandboxes now shared
across several analysts on different machines at different times, that is the daily
experience: close the desktop, walk away, the next person has to rekey, and the
person after them has to rekey again.

The wanted experience: *I close my desktop and leave; someone else types `start` and
is in.*

## 2. Decision: one shared credential per sandbox, SSM is the truth

Decided 2026-09-19 with the operator: **no per-analyst identity.** One keypair and one
desktop password per sandbox, shared by everyone who can run `km` against the install.
Rationale, stated so it is not re-litigated:

- Anyone who can run `km vscode start` already holds operator AWS credentials, which
  means they can `km shell --root` the box. The SSH key and desktop password are
  **convenience credentials**, not a boundary between analysts. Storing them shared
  costs nothing security-wise relative to the operator role.
- Per-analyst keys (each laptop appends its own pubkey via the pre-flight; no private
  key ever server-side; sshd logs name the laptop) were considered and declined —
  the operator does not need to tell analysts apart or lock one out selectively.
- Where the credential lives: **SSM is the source of truth; the local files are a
  cache.** The alternative — local-first, consult SSM only when the key "isn't valid"
  — cannot be built honestly: the ssh auth failure happens inside VS Code, herdr, or
  the browser, not in km's process (km only runs the port-forward). The only place km
  can observe validity is the SSM pre-flight it already makes, so "check SSM on
  failure" costs the same round trip as "check SSM always" and adds a second state.
- Not DynamoDB, not S3: it is a private key; the repo's rule is secrets go to SSM
  SecureString. (The desktop password already transits S3 as
  `remote-create/<id>/desktop-creds.txt` for the create-handler — that stays; it is a
  transit artifact, not a store.)

## 3. The store

Two SecureString parameters per sandbox, encrypted under the **platform** KMS key
(the same key the `/{prefix}/config/...` parameters use, exported by
`exportPlatformKMSKeyARN`):

```
/{prefix}/access/{sandbox-id}/ssh-key       # OpenSSH private-key PEM; pubkey DERIVED from it
/{prefix}/access/{sandbox-id}/desktop-cred  # "user:pass", byte-identical to ~/.km/desktop/<id>
```

**Why a new namespace and not `/{prefix}/sandbox/{id}/`.** The instance role is granted
`ssm:GetParameter*` on `parameter/{prefix}/sandbox/{id}/*` (`create.go` sandbox policy),
so anything parked there is readable by the box itself. The box has no business holding
its own operator private key. `/{prefix}/access/` is outside that grant. It IS inside
the operator policy's `parameter/{prefix}/*` grant (`ssm:GetParameter`,
`ssm:PutParameter`, `ssm:DeleteParameter`), so **no IAM change for laptops.**

**Why one parameter per credential, not two for the SSH key.** The public key is a pure
function of the private key (`gossh.ParsePrivateKey(...).PublicKey()`), and the key
comment (`km-<id>`) survives inside the OpenSSH PEM. One parameter means one read, one
write, and no "public and private disagree" state.

**Size.** An ed25519 OpenSSH PEM is ~400 bytes; a `user:pass` line is ~21. Both are far
under the 4 KB standard-tier limit. Standard tier, `Overwrite: true` on every write.

## 4. Behaviour

### 4.1 `start` — one sync function, four callers

`km vscode start`, `km herdr [start]`, `km tunnel k8s|socks` all locate the key through
`sandboxKeyPath(sandboxID)` (`internal/app/cmd/tunnel.go`). `km desktop start` has its
own inline locate in `runDesktopStart`. Both gain a call to one new function,
`syncSharedCredential`, which runs **before** the existing SSM pre-flight and
reconciles the local file to SSM:

| SSM | local | action | message |
|---|---|---|---|
| present | absent | write local (dir 0700, file 0600) | `✓ Pulled shared <kind> from SSM` |
| present | differs | overwrite local atomically (`.new` + rename) | `✓ Local <kind> refreshed from SSM (rekeyed elsewhere)` |
| present | same | nothing | (silent) |
| absent | present | `PutParameter` the local content | `✓ Published existing <kind> to SSM` |
| absent | absent | return an error naming the fix | `no shared <kind> for <id> in SSM and none at <path> — run: km vscode rekey <id>` (or `km desktop rekey`) |
| read error other than `ParameterNotFound` | present | WARN, continue with local | `[warn] could not read shared <kind> from SSM (<err>); using local copy` |
| read error other than `ParameterNotFound` | absent | return the read error wrapped with the path | — |

Row 4 is the migration path: every sandbox created before this ships is published to
SSM by the first `start` from a laptop that holds its credential. No backfill command,
no flag day.

Row 5 is the *pre-existing* cross-laptop bootstrap — `rekey` already supports "no local
key"; after this change it also publishes, so it is a complete fix rather than a
lockout-of-others.

The read-error rows are deliberate fail-open: this is a convenience credential, and an
SSM throttle or an expired SSO session between the laptop and SSM must never turn a
laptop that worked yesterday into one that does not.

For the SSH key, "differs" compares the private-key bytes after normalising the
trailing newline. For the desktop credential it compares the `user:pass` string after
trimming whitespace. On pull, the SSH sync also rewrites `~/.km/keys/<id>.pub` from the
derived public key (mode 0644), because `pubkeyFingerprint` and the doctor sweep read
it.

### 4.2 `rekey` — box → local → SSM

Both `runVSCodeRekey` and `runDesktopRekey` keep their existing sequence (lock gate,
confirm prompt, generate, SSM push with readback, atomic local commit) and gain one
final step: `PutParameter(Overwrite: true)`.

The order is load-bearing:

- **SSM before box would be wrong.** If the box push then failed, SSM would hold a
  credential the box rejects, and every laptop would pull a broken one.
- **Box → local → SSM.** If the last step fails, the operator who ran rekey is working
  (local is committed) and everyone else is stale until it is re-run. The error says
  exactly that:
  `rekey applied on the sandbox and locally, but publishing to SSM failed: <err>. Other analysts will get a stale credential until you re-run: km vscode rekey <id> --yes`
  and the §4.3 guard turns "stale" on any other laptop into a named fix.

`rekey` remains the only operation that invalidates a credential. `start` never does.

### 4.3 Mismatch guard (SSH only)

The pre-flight `vsCodeStatusScript` already returns the first line of the box's
`authorized_keys` under `=== authkeys content ===`. After sync, `parseVSCodeStatus`
gains an optional expected-pubkey argument: when the box line parses as an authorized
key and its fingerprint differs from the local key's, the error is

```
the sandbox's authorized_keys does not match the shared key in SSM — someone rekeyed
the box without publishing, or the box was restored from an AMI. Run: km vscode rekey <id>
```

instead of the `Permission denied (publickey)` the operator would otherwise meet inside
VS Code. `km herdr` runs the same check through its own pre-flight parser. `km tunnel`
makes no SSM pre-flight (it SSHes straight through the forward), so it gets the sync but
not the guard; a stale key there fails inside ssh with `Permission denied (publickey)`
and the fix is the same `km vscode rekey`.

**Desktop has no equivalent and this is stated in the docs, not papered over.**
`~/.kasmpasswd` stores a hash and `kasmvncpasswd` has no verify mode, so km cannot
check the password without a second, slower round trip. A stale desktop password
surfaces as a browser login failure; the fix is the same `km desktop rekey <id>`.

### 4.4 `create` publishes at generation time

Both `sshkey.GenerateAndWrite` call sites (local `runCreate` step 6d and
`runCreateRemote`) and both `GenerateDesktopCredential` call sites gain a publish
immediately after the local file is written. **Non-fatal**: a failed publish prints
`[warn] could not publish <kind> to SSM: <err> — other analysts cannot connect until
your next km <verb> start <id> (which republishes)`; the create proceeds. Row 4 of
§4.1 self-heals it.

The remote path publishes from the **laptop** — the create-handler Lambda never touches
`/{prefix}/access/`, so no create-handler IAM change.

### 4.5 Concurrency: last writer wins

`Overwrite: true`, no version CAS. Two analysts rekeying at the same instant can leave
the box holding one key and SSM the other. The §4.3 guard catches it on the next start
and names the fix. This is the "most basic key storage" the operator asked for; a
`ParameterVersion`-conditioned write is the upgrade if it ever bites in practice.

### 4.6 Cleanup on destroy

`pkg/aws.CleanupSandboxIdentity` deletes `signing-key`, `encryption-key` and
`safe-phrase` today and is called by both `km destroy` paths and the ttl-handler. It
gains `deleteSSMParameter` calls for both `/{prefix}/access/{id}/` parameters
(`ParameterNotFound` already swallowed — idempotent).

The ttl-handler's `IdentitySSMDelete` statement (`infra/modules/ttl-handler/v1.0.0`)
grants `ssm:DeleteParameter` per **exact name**, so it gains two ARNs. Edited in place,
additive, same as the budgets/schedules grants of 2026-09-02. A new guard test in
`pkg/terragrunt` pairs every parameter path `CleanupSandboxIdentity` deletes with an
ARN in that module's `IdentitySSMDelete` resources — name-agnostic, so the next
parameter added to cleanup is caught without editing the test.

### 4.7 `km doctor`

One new WARN-level check: `GetParametersByPath /{prefix}/access/` (recursive, no
decryption) and report any `{sandbox-id}` with no row in `{prefix}-sandboxes`. A remote
create that dies after key generation leaves one. Skipped silently when the path is
empty. Deletion is NOT offered — the existing local stale-keypair sweep
(`doctor_sshconfig.go`) is unchanged and remains the only deleter.

## 5. Out of scope

- `km roll creds` does not rotate the SSH key or desktop password today; unchanged.
- Per-analyst identity (decided against, §2).
- `km-presence`: an SSH session is signal 7 regardless of whose key opened it.
- The `remote-create/<id>/desktop-creds.txt` transit artifact.
- The `KM_DESKTOP_KASM_USER/PASS` env path inside the create-handler subprocess.

## 6. Security posture

- Parameters are SecureString under the platform CMK, in a namespace the sandbox role
  cannot read and the operator role already can. **Not a widening**: every reader
  already holds `ssm:StartSession` + `km shell --root` on the same box.
- The private key is at rest in SSM with the same protection as the GitHub App private
  key at `/{prefix}/config/github/...`.
- On the box nothing changes: `authorized_keys` content, sshd config, KasmVNC config
  are byte-identical.

## 7. Deploy surface

- **`make build`** delivers the whole experience. No userdata change, no SandboxProfile
  schema change, no sidecar, no sandbox recreate. Every existing sandbox joins on the
  first `start` from a laptop that holds its credential (§4.1 row 4).
- **`make build-lambdas` + `km init --dry-run=false`** for the ttl-handler cleanup
  grant (§4.6). NOT `--sidecars`. Until it lands, a TTL-expired sandbox leaves two
  orphan parameters that `km doctor` reports (§4.7) and that `km destroy` on the
  reaped row still cleans.
- Plugin version bump (`klanker:vscode` / `klanker:desktop` skill text changes).

## 9. Testing

Unit, against a fake `IdentitySSMAPI`:
- `syncSharedCredential` table: all seven rows of §4.1, for both kinds; the pull row
  asserts file modes and that the `.pub` is rewritten from the private key.
- Rekey: SSM put fails after local commit → error names the re-run and local files are
  the new key.
- Create: publish failure is a warning, not an error; publish content equals the file.
- `CleanupSandboxIdentity` deletes both new paths; not-found is swallowed.
- `parseVSCodeStatus` mismatch produces the §4.3 message; a box line that does not
  parse is not a mismatch (pre-existing boxes with odd content must not start failing).
- The §4.6 pairing guard fails when an ARN is removed (verified once by hand).

Live UAT (cheap — one machine simulates two laptops):
1. `km vscode start <id>` on the creator laptop → `✓ Published existing key to SSM`.
2. `HOME=/tmp/analyst2 km vscode start <id>` → `✓ Pulled shared key from SSM`, VS Code
   connects.
3. `HOME=/tmp/analyst2 km vscode rekey <id> --yes`; then on the creator laptop
   `km vscode start <id>` → `✓ Local key refreshed from SSM (rekeyed elsewhere)`,
   connects.
4. Same three steps with `km desktop`.
5. Hand-edit the box's `authorized_keys` via `km shell --root`; `km vscode start` →
   the §4.3 mismatch message.
6. `km destroy <id> --remote --yes` → both parameters gone.
