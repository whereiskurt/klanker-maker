# Wiz Outpost account connector

`km init --wiz` makes the AWS account a km install lives in a connected account
of an existing Wiz **Outpost** deployment, driven from `km-config.yaml`. Wiz can
then read the account's inventory, posture (CSPM) and run agentless disk scans.
Design: `docs/superpowers/specs/2026-11-10-wiz-outpost-connector-design.md`.

## 1. What it is

This is the **fourth** Wiz direction (see `docs/wiz-sensor.md` § 7): **Wiz reads
the account**. It shares no code or config with the other three
(`checks.triggers`, `webhooks:`, the runtime sensor).

km deploys Wiz's own Outpost cloud-connector CloudFormation template (vendored,
pinned, unmodified) as one stack named `{prefix}-wiz-outpost-connector`. The
stack creates:

- `WizAccess-Role` (name configurable): read-only, trusted by your Wiz tenant's
  data-center role, gated by `sts:ExternalId`.
- `WizScannerRole-<role_suffix>`: snapshot/volume/KMS work for disk scanning,
  trusted by `WizOrchestratorNodePoolRole` in your orchestrator account, same
  external id.

km does **not** deploy or manage the orchestrator, does not register the
connector in Wiz (you paste three values into the Wiz UI), and does not touch
linked capacity accounts. Dormant by default: with no `wiz:` block, nothing is
applied and `km doctor` makes zero AWS calls for it.

## 2. Prerequisites

- An Outpost orchestrator already running in another account, with other
  accounts already connected to it.
- From the Wiz UI, before you edit `km-config.yaml`:
  - **Tenant trust role ARN**: User Settings, then Tenant (the template's own
    description for `RoleARN`: "the AWS Trust Policy Role ARN for your Wiz data
    center").
  - **Orchestrator account id**: the 12-digit AWS account running the
    orchestrator.
  - **External id**: generated by the connector form in the Wiz UI (a nonce).
    It must be UUID-shaped (`xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`), the
    template's own `AllowedPattern`. It is stored in `km-config.yaml` in plain
    text; Wiz treats it as a confused-deputy nonce, not a secret.
- The credentials that apply the stack (the application-account SSO role that
  runs `km init`) need CloudFormation permissions to create, update, delete and
  describe the stack, plus IAM permissions to create, attach and delete the
  roles and policies for `WizAccess-Role` / `WizScannerRole-*`, and must be
  allowed to pass `CAPABILITY_NAMED_IAM`. km's own operator policy
  (`infra/modules/km-operator-policy`) does not grant `cloudformation:*`; an
  admin-equivalent SSO role works.

## 3. The `wiz.outpost:` block

All values below are synthetic.

```yaml
wiz:
  outpost:
    trust_role_arn: arn:aws:iam::444455556666:role/example-wiz-tenant-role
    orchestrator_account_id: "111122223333"
    external_id: "0a1b2c3d-0000-1111-2222-333344445555"
    role_suffix: "km"                 # scanner role becomes WizScannerRole-km
    access_role_name: WizAccess-Role  # optional; default shown
    scanning:                         # all optional; defaults shown
      data: false
      eks: false
      lightsail: false
      serverless: true
      cloud_cost: true
      rds_logs: true
      s3_aws_logs: true
      s3_kms_decrypt: true
      terraform_buckets: true
```

| Key | Required | Default |
|---|---|---|
| `trust_role_arn` | yes (IAM role ARN) | none |
| `orchestrator_account_id` | yes (12 digits) | none |
| `external_id` | yes (UUID-shaped) | none |
| `role_suffix` | yes | none |
| `access_role_name` | no | `WizAccess-Role` |
| `scanning.data` / `eks` / `lightsail` | no | `false` |
| `scanning.serverless` / `cloud_cost` / `rds_logs` / `s3_aws_logs` / `s3_kms_decrypt` / `terraform_buckets` | no | `true` |

- There is **no `disk` toggle**: disk scanning is always on (the template has no
  parameter for it; `WizScannerPolicy` is always attached to the scanner role).
- `isOrg` is always `Disabled`: single account, no StackSet.
- Validation runs at load. A missing or malformed key makes `km init` fail,
  naming the full key (for example `wiz.outpost.external_id is required`),
  before any terragrunt run.
- `km init` exports the block as `KM_WIZ_OUTPOST_JSON`; an env value that
  differs from the yaml produces a drift WARN (env wins), as for other blocks.
  A `KM_WIZ_OUTPOST_JSON` already set in the shell also applies when there is no
  yaml block at all (same as `KM_WEBHOOK_SOURCES`), again with the drift WARN.
- **One region.** IAM role names are global, so the live unit exists only under
  `infra/live/use1/` (the home region). A `km init` for any other region skips
  it and never creates a second stack.
- One install per account is assumed.

## 4. Apply

```bash
make build                         # BEFORE km init: the binary carries the new module entry
km init --wiz --dry-run            # shows what would apply
km init --wiz --dry-run=false      # or a full km init --dry-run=false
```

`--wiz` is tier-1 sugar for `--only wiz-outpost-connector` (no confirmation;
mutually exclusive with `--only`/`--github`/`--slack`/`--h1`/`--email`/
`--webhooks`, `--plan`, `--sidecars`, `--lambdas`). It errors if there is no
`wiz.outpost` block. A full `km init` applies the module too, and only when the
block is present (no plan, no state otherwise).

## 5. Paste into the Wiz UI

After a successful apply (scoped or full) km prints:

```
Wiz Outpost connector — paste into the Wiz UI:
  Access role ARN   arn:aws:iam::111122223333:role/WizAccess-Role
  Scanner role ARN  arn:aws:iam::111122223333:role/WizScannerRole-km
  External ID       0a1b2c3d-0000-1111-2222-333344445555
```

Enter these in the connector form. To reprint them later, along with the stack
status and deployed template version:

```bash
km wiz status
```

If the outputs cannot be read after an apply, km prints a one-line warning
pointing at `km wiz status`; the apply itself is not failed.

## 6. What `km doctor` checks

Only when `wiz.outpost` is configured (otherwise zero AWS calls):

- **Wiz Outpost connector stack**: the stack exists, is `CREATE_COMPLETE` or
  `UPDATE_COMPLETE`, and its `WizVersionLastUpdated` parameter equals the
  vendored template's. WARN otherwise, with `km init --wiz --dry-run=false`.
- **Wiz Outpost connector trust**: `iam:GetRole` on both roles; the trust policy
  must name the configured principal (tenant role ARN for the access role,
  `WizOrchestratorNodePoolRole` in the configured orchestrator account for the
  scanner role) and the configured `sts:ExternalId`. This catches a hand-edited
  trust policy and a yaml edit that was never applied.

Doctor's orphan sweeps (orphaned EBS volumes, untagged available volumes,
orphaned snapshots) skip any volume or snapshot tagged `wiz` =
`auto-gen-volume`, `auto-gen-snapshot` or `shareable-resource`, so
`km doctor --delete-ebs` never removes Wiz's temporary scan resources. This
applies regardless of configuration.

A stack left behind after the `wiz:` block is removed is reported by
`km wiz status`, not by doctor.

## 7. Template bump procedure

The template is Wiz's own file, vendored as
`infra/modules/wiz-outpost-connector/v1.0.0/wiz-outpost-connector.json`
(v1.0.0 ships the public copy, `WizVersionLastUpdated: 2025-10-07`). It is never
fetched at apply time, so a Wiz-side change cannot alter scanning permissions
without a reviewable diff.

1. Export the current Outpost connector template from your Wiz tenant, or take
   the Terraform/CloudFormation the other accounts use.
2. Create `infra/modules/wiz-outpost-connector/v1.1.0/` as a copy of `v1.0.0/`
   with the new JSON in place (module versions are immutable; never edit v1.0.0).
3. Repoint `infra/live/use1/wiz-outpost-connector/terragrunt.hcl` (`terraform.source`) at `v1.1.0`.
4. Run `go test ./pkg/wizoutpost/`. The contract test names any parameter or
   output the new template renamed or dropped, and checks the minified template
   stays under CloudFormation's 51,200-byte inline limit (if it does not, the
   module must stage it in S3 and use `template_url`; not built yet).
5. `km init --wiz --dry-run`, review, then `km init --wiz --dry-run=false`.
6. Confirm the connector stays healthy in the Wiz UI and `km doctor` is green.

## 8. Removing it

1. Remove the connector in the Wiz UI first.
2. Then `km uninit` (destroys the stack when its state exists; it does not need
   `KM_WIZ_OUTPOST_JSON`), or delete the stack yourself.

Removing the `wiz:` block from `km-config.yaml` alone destroys nothing: `km init`
just skips the module, and `km wiz status` reports that the stack still exists.

## 9. Troubleshooting

- **Stack in `ROLLBACK_COMPLETE`**: read the stack events in CloudFormation. The
  usual cause is a role name already taken, for example a `WizAccess-Role`
  created by hand earlier. Delete or rename the old role (or set
  `access_role_name`), delete the failed stack, and re-run `km init --wiz`.
- **Doctor reports a trust mismatch**: the live role differs from
  `km-config.yaml` (hand edit, or a yaml change never applied). Re-apply with
  `km init --wiz --dry-run=false`.
- **Disk scans fail inside Wiz with no km-side symptom**: if km's
  `{prefix}-sandbox-containment` SCP is attached to the account, it denies the
  scanner's snapshot actions: the v3 SCP (`scp-from-config`) denies
  `ec2:DeleteSnapshot`, the v2 SCP denies `ec2:CreateSnapshot`/`CopySnapshot`.
  km does not warn about this in this release. Check with the SCP doctor check ("SCP
  content") or `km bootstrap --scp-only --plan` where available.
- **Access errors in other regions**: expected if the account is region-restricted
  elsewhere; not a km bug.

## 10. Deploy surface

`make build`, then `km init --wiz --dry-run=false` (or a full
`km init --dry-run=false`). No Lambda, sidecar, userdata, profile schema change,
and no sandbox recreate. Existing installs with no `wiz:` block are unaffected.

## 11. Live UAT

**Run 2026-11-10 against a real application account with stand-in trust roles.** No Wiz tenant
was available, so the "Wiz tenant" principal was a permissionless role in the same account and the
"orchestrator" was a permissionless role named `WizOrchestratorNodePoolRole` in that account. IAM
validates that a trust-policy principal exists at `CreateRole`, so made-up ARNs would have failed the
apply. Both stand-ins were deleted afterwards. This exercises everything km owns; the Wiz-side rows
need a real tenant.

- [x] `km init --wiz --dry-run` with no `wiz:` block fails before any AWS call (`wiz-outpost-connector (--wiz) requires a wiz.outpost block in km-config.yaml`); `km doctor` registers no Wiz checks.
- [x] With the block: `terragrunt plan` of the unit shows `1 to add`, with `WizVersionLastUpdated = "2025-10-07"` in the stack parameters. `km init --wiz --dry-run=false` created the stack in under a minute and printed the three values. `WizAccess-Role` trusts the tenant principal and `WizScannerRole-km` trusts `WizOrchestratorNodePoolRole`, both with the external id; the expected managed and inline policies are attached.
- [x] `km wiz status` shows `CREATE_COMPLETE`, template `2025-10-07`, and the paste-out.
- [x] `km doctor` "Wiz Outpost connector stack" and "… trust" are green; with a different `external_id` in yaml (not applied) the trust check WARNs `role WizAccess-Role sts:ExternalId does not match wiz.outpost.external_id`.
- [x] With the `wiz:` block removed and the stack still present, `km wiz status` warns that the stack exists but is not configured; `km doctor` shows no Wiz rows.
- [x] Destroy of the unit with `KM_WIZ_OUTPOST_JSON` unset (the `km uninit`-after-removal path, run as a single-unit `terragrunt destroy` rather than a full `km uninit`) removed the stack and both roles.
- [ ] Paste into the Wiz UI; the connector reaches healthy and account inventory appears. *(needs a Wiz tenant)*
- [ ] A disk scan of a long-lived sandbox completes; Wiz's temporary volume/snapshot appear tagged `wiz=auto-gen-*`; `km doctor` does not list them as orphans. *(needs a Wiz tenant)*

Two findings, both fixed: `km env` did not export `KM_WIZ_OUTPOST_JSON` (a hand-driven plan would
have used empty parameters), and the scoped apply ended with the bridge-Lambda "stale code zip" notes.
