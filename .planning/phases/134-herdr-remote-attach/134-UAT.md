### Step 2 — fragment installs at boot — **PASS**

`km herdr status herdruat` →

### Step 2b (NEW) — the S3 path is the ONLY path — **PASS**

The plan had no step proving the fragment does anything. After #106 it needed one:
`base/userinit` now fetches herdr from a SHA-pinned `github.com` asset, and
`base/network/locked` allows `.github.com`, so the fragment is redundant on every
existing profile. `profiles/uat-herdr.yaml` exists to be the one case where it is not.

| assertion | observed |
|---|---|
| `/usr/local/bin/herdr` | present, 22,733,040 b, `herdr 0.8.2`, root 0755 |
| `~sandbox/.local/bin/herdr` | **absent** — userinit genuinely not in play |
| real `[km] herdr fetch failed` lines in cloud-init log | **0** |
| `github.com` DNS | **NXDOMAIN** |
| `objects.githubusercontent.com` DNS | **NXDOMAIN** |
| sandbox login-shell `curl https://github.com/` | `curl: (56) Proxy CONNECT aborted`, HTTP 000 |
| `s3.amazonaws.com` (positive control) | resolves; mirror listable from the box |
| box binary SHA-256 | `976150a14d490c94b243ea2e1a7eb2dfb67f12e36b182db90936f6728e6aecf4` |

That digest is exactly `herdrSHA256` in `internal/app/cmd/init.go`. GitHub was
unreachable at both DNS and proxy layers, so S3 was the only possible source and the
binary matches the source pin byte for byte.

The curl was run via `sudo -iu sandbox bash -lc` — a **login** shell. A bare
`sudo -u sandbox curl` skips `HTTPS_PROXY` and egresses direct, which would have
produced a false negative.

### Step 4 — signal 8 positive, headless — **PASS**

Nothing ever attached. Work was a plain `sleep`, so agent-agnosticism is exercised,
not asserted.

Pane-level A/B on `w1:p1`:

| | `foreground_process_group_id` | `shell_pid` | busy | `foreground_processes` |
|---|---|---|---|---|
| idle | 31645 | 31645 | **False** | `['sh']` |
| `sleep 900` | 31732 | 31645 | **True** | `['sleep']` |

`foreground_processes` is `['sh']` **when idle** — non-empty. The plan's original
`len(foreground_processes) > 0` check would therefore have been permanently true,
silently disabling idle teardown fleet-wide. Confirmed live, not just in fixtures.

Daemon-level, from km-presence's own journal:

```
        pam_unix(runuser:session): session opened for user sandbox   x3  <- signal 8 probes
4:53AM  presence tick complete active=true  emitted=true  tick=7
```

Competing signals all silent at the time: `who`=0, claude/codex=0, Xvnc=0,
sshd sessions=0, mail=0, slack stamp absent. **Signal 8 alone flipped the daemon.**

At 05:03:16Z — 16 min uptime, well past the 04:56:30 idle deadline — instance still
`running`, ticks 11–16 all `active=true emitted=true`, `sleep 900` alive.

### Step 5 — signal 8 negative — **PASS (this is the merge gate)**

Job killed; **herdr server deliberately left running** with only idle panes.

```
5:03AM  presence tick complete active=true  emitted=true  tick=17
5:04AM  presence tick complete active=false emitted=false tick=18
5:05AM  presence tick complete active=false emitted=false tick=19
```

Then, with no further box contact:

```
05:03      last heartbeat
05:14:02   stopping — StateTransitionReason: "User initiated"
```

CloudWatch `/aws/lambda/km-ttl-handler` attributes it, so this is an idle reap and
not the 3h TTL:

```json
{"sandbox_id":"uatherdr-511e0afc","event_type":"idle","teardown_policy":"stop",
 "message":"teardownPolicy is 'stop' — stopping instead of destroying"}
```

**Signal 8 can go negative with a live Herdr server present.** That is the failure
mode — a signal that can never go negative — which would have disabled idle teardown
across the fleet.

### Step 5b — OPERATOR-RUN — **PASS** (operator, 2026-09-05)

Operator ran `km herdr start herdruat` and attached with
`herdr --remote km-uatherdr-511e0afc`. The connection succeeded. This was the last
claim in the phase that no automation could cover.

Evidence captured from the box afterwards:

- `herdr pane list` shows **`pane w3:p1`** — a workspace the headless driving never
  created (it made `w1`), so the interactive session was real and independent.
- km-presence ticks 19–22 `active=true`, tick 23 `active=false` once the operator
  disconnected. Signals 7 and 8 dividing the work exactly as designed: 7 sees the
  *attached* client (a herdr client is an SSH session), 8 covers *detached-but-busy*.

**`herdr agent list` returned `{"agents":[]}`** on this box, and the operator saw
Herdr report no claude/codex. That is this profile's design, not a defect:
`profiles/uat-herdr.yaml` deliberately omits `base/userinit` (which installs the
agents) and `base/os/redhat` (node/npm) — confirmed live, all four of `claude`,
`codex`, `node`, `npm` absent. The omission is what made step 2b provable: had
userinit run, its own `~sandbox/.local/bin/herdr` would have masked whether the S3
fetch worked.

It also re-confirms §6.4 decision #2 on a second box: `agent list` cannot drive
signal 8 because it reports only *recognised* agents, and returns `[]` otherwise —
matching `cmd/km-presence/testdata/herdr_agent_list_empty.json`. Signal 8 read
`process-info` instead and worked on a plain `sleep`. Agent-agnosticism exercised,
not asserted.

Not covered by this run: `ctrl+b q` detach followed by reattach to the *same*
session. The attach itself is proven; the detach/reattach round trip is not.

### Step 6 — lifecycle claim — **PASS, and it FALSIFIED the shipped claim**

Both paths measured on the same box.

| | idle reap (`hibernation: true`) | `km stop` |
|---|---|---|
| boot time across the cycle | **unchanged** 04:46:30 | **new** 05:29:51 |
| `hibernation exit` in `dmesg` | present (`Waking up from system sleep state S4`) | **0 lines** |
| `herdr server` | **same pid 31566** | gone |
| API socket | present | **GONE** |
| detached pane job | survived | gone |
| `/usr/local/bin/herdr` | present | present (root volume) |

`km herdr start`'s help text and the runbook both said an idle stop under
`teardownPolicy: stop` kills every pane unconditionally. **False for any profile with
`hibernation: true`.** `cmd/ttl-handler/main.go` calls `lookupHibernation`, reads
`profile.Spec.Runtime.Hibernation` from the stored profile, and issues
`StopInstances` with `Hibernate: true` when set — falling back to a plain stop only
on `UnsupportedHibernationConfiguration`. `internal/app/cmd/stop.go:139` never passes
that flag, which is why the two paths differ.

Not reachable by code review: the code is correct, the *claim about it* was wrong,
and only a real reap on a hibernation-enabled box distinguishes them. Both sites
corrected on this branch.

## 3. Not verified

- **The `ctrl+b q` detach → reattach round trip.** The interactive attach itself is
  now verified (step 5b), but the operator did not exercise detach-and-reattach to
  the same session. Pane survival across *detach* is proven headlessly — panes
  outlived the SSM channel and a hibernate — so this is a UI-level gap, not a
  behavioural one.
- **`km herdr status`'s pre-signal-8 warning branch** was not re-exercised this
  session — every box now carries signal 8. Verified in the first session only.
- **A profile with `hibernation: false`** was not tested. The `km stop` path proves
  panes die on a true stop, and `lookupHibernation` returning false takes the same
  `StopInstances` call, so the behaviour is argued from shared code rather than
  observed.
- **Remote cold-create of a profile extending `base/tools/herdr`** works only because
  `runCreateRemote` resolves the DAG locally and uploads the merged profile. The
  fragment is not in the deployed `infra.tar.gz` and will not be until this branch
  merges.
