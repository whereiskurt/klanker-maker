    Prerequisites, confirmed before starting:
    1. Administrator credentials for the capacity account are available as a named profile.
    2. Home-account credentials are available as the usual profile.
    3. The GPU vCPU quota for running on-demand G and VT instances has headroom in the
       TARGET account and region. Verify it in that account directly — the organization's
       management console shows a different account's quota, and this specific confusion has
       already cost this project two phases of deferred verification.
    4. The operator binary and the Lambdas have been rebuilt and applied per the deploy
       section of the new runbook, in the stated order.

    Containment proof (no spend, run first):
    5. Run the eight-row policy simulation from `126-UAT.md` against the live launcher role,
       one simulation per row. Record the actual verdict beside each expected verdict. Every
       deny row must actually deny. A single unexpected allow is a blocking finding — stop
       and report rather than proceeding to the launch steps.

    Live steps:
    6. Run the enrollment command with the capacity account's administrator profile and
       network provisioning enabled. Confirm the launcher role, box role, permissions
       boundary, results bucket, and one subnet per availability zone all exist in that
       account, and that a link fragment was written with owner-only permissions.
    7. Run the registration command with home-account credentials. Confirm the link appears
       in the configuration, the external id is stored as an encrypted secure parameter, and
       exactly one read-only statement was added to the artifacts bucket policy.
    8. Run `km doctor` and confirm all four new checks report healthy.
    9. Run the capacity report against the link and confirm it reports the TARGET account's
       GPU headroom, not the home account's. This is the single most important observation
       in the whole verification — if the numbers look like the home account's, the phase's
       central bug is still present.
    10. Create a GPU sandbox from a profile naming the link, on the LOCAL path. Confirm the
        instance appears in the target account, carries the km tags, sits in a km subnet,
        and is reachable through the platform's shell. Confirm the sandbox row in the home
        account records the link's account id.
    11. Destroy that sandbox and confirm the instance is gone from the target account and
        the home-account row is cleaned up.
    12. Repeat the create on the REMOTE path and destroy it the same way.
    13. Create one more with a short lifetime and leave it. Confirm the expiry Lambda reaps
        it unattended, that the instance is gone from the target account, and that the
        home-account row is cleaned up.
    14. Delete the local sandbox directory for a linked sandbox and run destroy again, to
        exercise the cold-clone path specifically. Confirm it succeeds rather than reporting
        the sandbox as not found.
    15. Create a home-account sandbox from a profile with no link and confirm nothing about
        it changed — this is the dormancy check against a live install.
    16. Run the removal command and confirm the home-side link, parameter and grant are gone
        and the target-account footprint is destroyed.

    Destroy-flag convention (applies to steps 11, 12, 14 and 16): this project's teardown
    invocation is `km destroy <id> --remote --yes`. There is no `--force` flag on destroy —
    do not invent one. Use the `--remote --yes` form in every teardown step above and in the
    runbook Task 1 writes.

    Record every step's outcome in `126-UAT.md`, including any step deferred for quota or
    cost reasons, with the reason stated.
  </how-to-verify>
