## Decisions recorded by this plan

Two questions RESEARCH.md flagged as non-blocking are settled here, with the reasoning
written into the code comments so a later reader does not re-litigate them:

1. **`km account add` uses real terraform, not a command-printing wizard.** `km account rm`
   is specified to tear the target-account footprint back down, and a clean idempotent
   teardown needs real state to destroy against. This is a deliberate divergence from the
   service-control-policy bootstrap's print-the-commands mechanism, which has no state.
2. **The generated unit is standalone on BOTH the provider and the backend** — no root
   include, a local backend, and its own plain provider. Reusing the home account's shared
   S3 backend while authenticated as the target account produces exactly the access-denied
   the roadmap already records as the reason `km create --aws-profile <management>` was
   rejected. No existing unit in this repo is standalone on both dimensions; that is
   novelty, not oversight.
3. **The unit and its state live under the operator's home directory, not in the repo.**
   Terraform state for this module contains the trust policy, and therefore the external
   id, in plaintext. Keeping it out of the working tree removes the possibility of
   committing a secret, which a repo-relative unit would depend on a gitignore rule to prevent.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator shell → target account admin credentials | this is the single most privileged moment in the whole feature; it happens once, by hand |
| minted external id → local disk | the secret exists on the operator's workstation in the unit's terraform state and in the link fragment |
| generated unit → terraform state backend | a wrong backend choice would either fail loudly or, worse, put target-account state in the home account's bucket |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-126-23 | Information Disclosure | external id on local disk | high | mitigate | The unit directory, its state, and the link fragment are all created under the operator's home directory at owner-only permissions, outside the git working tree, so the secret cannot be committed. The value is never echoed to the terminal; the operator is pointed at the fragment path instead. |
| T-126-24 | Spoofing | empty external id | high | mitigate | The command always resolves an external id — supplied, decrypted, or minted from a cryptographically secure source — and the module itself rejects an empty value, so a condition-free trust policy cannot be produced by either layer. |
| T-126-25 | Elevation of Privilege | wrong-profile enrollment | high | mitigate | The resolved caller account id is printed, and the command fails when it equals the trust account id — enrolling the home account into itself would create a standing self-trust door. |
| T-126-26 | Tampering | incomplete trust list | high | mitigate | All three principals are authored on the first apply. The plan's own decision record and the printed trust list make an omission visible at enrollment time, when target-account credentials are still in hand. |
| T-126-27 | Elevation of Privilege | backend credential confusion | medium | mitigate | The generated unit is standalone with a local backend, so the target account's administrator credentials never touch the home account's shared state bucket. |
| T-126-28 | Repudiation | no state, no teardown | medium | mitigate | Real terraform with real state is used specifically so `km account rm` can destroy exactly what was created rather than leaving the operator a manual checklist. |
</threat_model>
