## Decisions recorded by this plan

Two questions RESEARCH.md flagged as non-blocking are settled here, with the reasoning
written into the code comments so a later reader does not re-litigate them:

1. **`km account add` uses real terraform, not a command-printing wizard.** `km account rm`
   is specified to tear the target-account footprint back down, and a clean idempotent
   teardown needs real state to destroy against. This is a deliberate divergence from the
   service-control-policy bootstrap's print-the-commands mechanism, which has no state.
2. **The generated unit is standalone on BOTH the provider and the backend** — no root
   include, its own plain provider, and its own S3 backend **in the target account**.
   Reusing the home account's shared S3 backend while authenticated as the target account
   produces exactly the access-denied the roadmap already records as the reason
   `km create --aws-profile <management>` was rejected. No existing unit in this repo is
   standalone on both dimensions; that is novelty, not oversight.
3. **There is NO local Terraform state — not for this unit, not anywhere.** This is a
   hard operator constraint, not a preference. The enrollment unit's state lives in an S3
   bucket with a DynamoDB lock table, both **in the target account**, both created by
   `km account add` itself through the AWS API immediately before the first `terragrunt
   init`. Because enrollment authenticates as the target account for the provider AND the
   backend, there is no cross-account credential split in this command at all — it is
   strictly simpler than the sandbox launch path, which keeps state at home and assumes
   only for the provider.

   The backend is shared per (resource prefix, target account, region) and keyed per link,
   so enrolling a second link into the same capacity account reuses the same bucket and
   table under a different state key. Naming, all deterministic so `rm` and a fresh clone
   can rediscover them:
   - bucket `tf-{prefix}-linkstate-{target-account-id}-{region-label}` — the account id is
     in the name because S3 bucket names are globally unique
   - lock table `tf-{prefix}-linklocks-{region-label}` — per-account, so no global uniqueness
     concern
   - state key `account-links/{name}/terraform.tfstate`

   Both identifiers are recorded in the link fragment and the link record, so teardown never
   has to guess and never depends on a file surviving on one operator's laptop.
4. **The generated unit directory stays under the operator's home directory.** It is a
   regenerable artifact, not a source of truth — the link record carries everything needed
   to reproduce it. Keeping it out of the working tree means the external id, which is
   rendered into the unit's inputs, cannot be committed by accident.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator shell → target account admin credentials | this is the single most privileged moment in the whole feature; it happens once, by hand |
| minted external id → local disk | the secret exists on the operator's workstation in the generated unit's inputs and in the link fragment — but NOT in a state file, because state is remote |
| minted external id → target-account state bucket | the state object records the trust policy, so the external id is stored in the target account |
| generated unit → terraform state backend | a wrong backend choice would either fail loudly or, worse, put target-account state in the home account's bucket |
| backend bootstrap → a bucket name that already exists elsewhere | S3 bucket names are global; a name collision must not be mistaken for "already mine" |
