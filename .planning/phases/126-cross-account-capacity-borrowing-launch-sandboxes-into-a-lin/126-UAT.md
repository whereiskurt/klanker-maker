#### Finding L1 — `ec2:RunInstances` is not tag-gated (Row 4) — **MITIGATED, and the fix originally proposed here was WRONG**

> **CORRECTION 2026-08-25.** The remedy this finding recommended — adding
> `StringEquals { "aws:RequestTag/km:managed-by" = "klankermaker" }` to `LaunchOnlyGpuBoxes` —
> **must not be applied. It had already been tried and reverted during the phase**, and
> re-adding it would break every cross-account launch.
>
> `infra/modules/gpu-launcher-account/v1.0.0/main.tf` records why, from a live
> `sts decode-authorization-message`: for the `instance/*` resource of a `RunInstances` call
> AWS populates **exactly two** condition keys — `ec2:AvailabilityZone` and `ec2:InstanceType`.
> It populates **no `aws:RequestTag/*` keys and no `ec2:Subnet`**. A condition on any of those
> is therefore *unsatisfiable*: the statement never matches and every launch fails with
> `no identity-based policy allows the ec2:RunInstances action` — the message AWS emits for an
> unsatisfiable condition, which reads exactly like a missing statement. Commit `0d362066`
> removed those conditions for that reason.
>
> **Why the finding still reached the wrong conclusion:** `simulate-principal-policy` will
> happily evaluate a condition key against context you supply, whether or not AWS ever
> populates that key in the real call. Row 4's `allowed` verdict was a correct *simulation*
> result and a misleading guide to the fix. **A simulator verdict proves what the policy says,
> not what AWS can enforce at call time.**
>
> **The risk is real, so it is now mitigated by detection instead.** Tag-gating is impossible at
> the IAM layer, so `checkLaunchAccountOrphanInstances` was changed to stop filtering
> `DescribeInstances` on `tag:km:sandbox-id` and to classify in code: an instance whose sandbox
> id is unknown to home **or absent entirely** is reported as an orphan, the untagged case
> labelled `<untagged>` with remediation noting that `km destroy <sandbox-id>` cannot reap it.
> That filter was the reason the check could not see the very leak it exists for.

`LaunchOnlyGpuBoxes` allows `ec2:RunInstances` on `instance/*` under an `ec2:InstanceType`
condition only. There is no `aws:RequestTag/km:managed-by` condition on it, so a `RunInstances`
call supplying **no** km tag is `allowed`. The matrix predicted `implicitDeny`.

**Why it matters — the two halves interlock badly.** An untagged instance is:

- **un-reapable by the launcher role** — `LifecycleTaggedOnly` gates
  `ec2:TerminateInstances` / `ec2:StopInstances` on
  `aws:ResourceTag/km:managed-by=klankermaker` (Row 6, verified with a positive control). The
  role that created the box cannot terminate it.
- **invisible to the safety net built for exactly this** — `checkLaunchAccountOrphanInstances`
  in `internal/app/cmd/doctor.go` filters `DescribeInstances` on `tag:km:sandbox-id = *`. An
  instance carrying no km tags does not match that filter, so the Phase 126 doctor check whose
  stated purpose is "no orphaned linked-account EC2 instances (a leaked box `km list` cannot
  see, billing silently)" would not see it either.

The result is a GPU instance that bills indefinitely and is discoverable only with
target-account admin credentials — the precise failure that check was written to prevent.

**Severity: hardening gap, not a live exploit.** Reaching `RunInstances` at all requires
assuming the launcher role, which requires being one of the three trusted home-side principals
*and* holding the `sts:ExternalId`. km's own create path always tags. Nothing in the shipped
code path produces an untagged box today. This is defense-in-depth — but the phase documents
this IAM policy as the **entire** containment boundary for an SCP-exempt target account, and on
this row the boundary does not enforce what the phase record says it enforces.

**Suggested fix.** Add to `LaunchOnlyGpuBoxes` in
`infra/modules/gpu-launcher-account/v1.0.0`:

```hcl
condition {
  test     = "StringEquals"
  variable = "aws:RequestTag/km:managed-by"
  values   = ["klankermaker"]
}
```

**Why this is lower-risk than it first looks.** The obvious objection is that the condition
fails closed on any launch not tagged *at `RunInstances` time*, and this phase already tripped
over tag timing once — commit `7433c1bc` ("authorize tag-on-create via `ec2:CreateAction`; give
the on-demand path `volume_tags`") exists because the on-demand path was not tagging where it
was assumed to. Two facts narrow that risk:

1. The spot path **cannot run cross-account at all** (no `RequestSpotInstances` grant, verified
   above), so only the on-demand path needs to survive the condition.
2. The on-demand path tags the instance resource directly —
   `aws_instance.ec2_ondemand` in `infra/modules/ec2spot/v1.3.0/main.tf:764-771` sets
   `km:managed-by = "klankermaker"` in its `tags` block, which the AWS provider submits as
   `TagSpecifications` on the `RunInstances` call itself. That is exactly the `aws:RequestTag`
   the condition would test.

**Still not applied in this session**, because it is a policy change to the one boundary
protecting an SCP-exempt account and it belongs with its own live create to confirm, rather
than riding along on a UAT run whose purpose was to prove vLLM serves a token. Recommended as a
small follow-up, not a blocker.

Found 2026-08-24 while running REQ-126-UAT. This is the real cause of the
`sb-be0fdcb8` failure that `126-HANDOFF.md` attributed to "a leftover lock from an earlier
aborted run" — the leftover lock was created by the create-handler Lambda's own 900s timeout,
and the timeout was caused by this.

**What happens.** `capacity.RankAZs` applies sticky-AZ preference and picks the AZ with the most
recent success. For `481723467561#g6e.12xlarge` that row is `us-east-1a`
(`last_success_at=1787543307`, the 03:48Z `sb-58e176df` launch). If `us-east-1a` has since gone
capacity-dry, terraform calls `RunInstances` there, gets
`Server.InsufficientInstanceCapacity`, and **retries internally, in the same AZ, indefinitely**.
km never receives the ICE error, so `sweepDecision` is never reached, so the AZ never rotates.
The Lambda burns its whole 900s budget on one dry AZ and is killed mid-apply, leaving the
state lock behind. EventBridge then retries the event twice; both fail-fast on that lock with
`Error acquiring the state lock`, which is the only error a reader ever sees.

**Observed, this run** (`sb-ceffcb7c`, dispatched 13:37:17Z):

```

    AttributeKey=EventName,AttributeValue=RunInstances \
    --region us-east-1 --profile <target-admin>

13:38:51Z  13:39:29Z  13:40:49Z  13:43:14Z  13:47:32Z   <- 5+ attempts, all us-east-1a
```

with every event carrying:

AWS is naming a working AZ in the error text while km retries the dry one.

**Diagnostic trap worth recording.** `aws cloudtrail lookup-events --query
'Events[].[EventTime,Username,ErrorCode]'` prints `ErrorCode: None` for every one of these
events, because `ErrorCode` is not a top-level `lookup-events` field — it lives inside the
`CloudTrailEvent` JSON blob. Reading the summary projection alone gives the confident and
entirely wrong conclusion that `RunInstances` is succeeding. The error is only visible by
parsing `Events[].CloudTrailEvent`. (That blob also does not `json.load` cleanly — it needs
`json.JSONDecoder().raw_decode()`.)

**Severity: real, and not cross-account-specific.** Nothing here depends on the launch being
cross-account — a home-account GPU launch into a sticky-but-dry AZ hits the same wall. Phase
126 only makes it easy to notice, because a linked GPU account is where scarce capacity lives.
The remote path is worse than the local path solely because of the 900s ceiling: locally the
sweep would eventually rotate once terraform gave up, just slowly.

**Two things to consider (neither applied here — both are their own change):**

1. Bound the provider-level retry so km sees the ICE and can classify it — the Phase 124 sweep
   is already written to handle it and never gets the chance.
2. Have `RankAZs` treat AWS's own "you can currently get capacity in X" hint as a signal, or at
   minimum record ICE against the attempted AZ *as attempts fail* rather than only after
   terraform gives up. `bestEffortRecordCapacity` cannot fire today because control never
   returns to km.

**Workaround used to unblock this UAT:** write the ICE row that `RecordICE` would have written,
so `RankAZs` deprioritizes the dry AZ:

```
aws dynamodb update-item --table-name km-capacity --region us-east-1 \
  --key '{"instanceType":{"S":"481723467561#g6e.12xlarge"},"az":{"S":"us-east-1a"}}' \
  --update-expression "SET last_ice_at = :ice, #ttl = :ttl" \
  --expression-attribute-names '{"#ttl":"ttl"}' \
  --expression-attribute-values '{":ice":{"N":"<now>"},":ttl":{"N":"<now+2700>"}}'
```

This is the table's own designed mechanism (`pkg/capacity/store.go:82`, `ICETTLSeconds = 2700`),
the row self-expires in 45 minutes, and the fact it records is true — AWS refused that AZ five
times.

**The workaround was confirmed to take effect**, which also proves the ranking half of the
Phase 124 machinery is sound and that only the error-propagation half is broken. Before, the
linked-account table held exactly one row (`us-east-1a`, success, no ICE), so the sticky
preference had no competing signal. After writing the ICE row, `km capacity` re-ranks:

```
AZ          OFFERED  QUOTA HEADROOM  LAST ICE           LAST SUCCESS       VERDICT
us-east-1a  yes      768 vCPU        2026-08-24T13:57Z  2026-08-24T03:48Z  recently-dry
us-east-1b  yes      768 vCPU        —                  —                  likely
us-east-1c  yes      768 vCPU        —                  —                  likely
us-east-1d  yes      768 vCPU        —                  —                  likely
```

`RankAZs` correctly demotes the dry AZ to `recently-dry` and promotes the untried ones to
`likely`. So the sweep *would* have rotated on its own the moment it saw the ICE — it simply
never sees it, because terraform retries internally until the Lambda is killed. That narrows the
fix to error propagation and rules out the ranking logic.

#### Finding L3 — `rankScore` short-circuits on success, so a fresh ICE can never demote an AZ that once worked (ROOT CAUSE) — **FIXED**

> **RESOLVED 2026-08-25.** `rankScore` now evaluates freshness before stickiness, and
> `ComputeCapacityVerdict` carries a cross-reference comment so the two implementations cannot
> drift apart again. Two regression tests were added, both of which fail against the old
> ordering:
>
> - `TestRankAZs_FreshICEOutranksStaleSuccess` — an AZ holding BOTH a last-success and a fresh
>   ICE must rank **last**, below AZs with no history at all. This is the case the existing
>   `TestRankAZs_ICEStickySuccess` never reached, because there each AZ carried only one of the
>   two attributes — which is how the defect survived a green suite.
> - `TestRankAZs_VerdictAgreesWithRanking` — also pins the boundary the fix must not overshoot:
>   an **expired** ICE (outside the 45-min window) still lets stickiness apply, so the change
>   demotes genuinely-dry AZs without discarding sticky-AZ history.
>
> The fix does not address **L2** (terraform still retries ICE internally), so a dry AZ still
> costs one full create-handler timeout — but the sweep no longer returns to the same dry AZ on
> every subsequent launch.

Found 2026-08-24, after the Finding L2 workaround did **not** work. This is the deeper defect;
L2 is a compounding factor, not the whole story. **This is not cross-account-specific and is not
a Phase 126 bug** — it is in the Phase 124 capacity ranker and affects home-account launches
identically.

`pkg/capacity/rankaz.go:129`:

```go
func rankScore(ctx context.Context, store CapacityStore, instanceType, az string) int {
    entry, err := store.Get(ctx, instanceType, az)
    if err != nil || entry == nil {
        return 0
    }
    if entry.LastSuccessAt != nil {
        return 2                 // <-- checked FIRST, returns unconditionally
    }
    if entry.LastICEAt != nil && time.Since(*entry.LastICEAt) < freshICEWindow {
        return -1                // <-- unreachable for any AZ that ever succeeded
    }
    return 0
}
```

An AZ holding **both** a `last_success_at` and a fresh `last_ice_at` scores **2 — the maximum**.
The ICE branch is never evaluated. And because success rows are written with **no TTL** and
persist forever (deliberately, for sticky-AZ history), *once an AZ has ever succeeded it
outranks every other AZ permanently, no matter how many times it subsequently ICEs.*

**The feedback loop Phase 124.07 describes is therefore inert in exactly the case it exists
for.** `bestEffortRecordCapacity` faithfully calls `RecordICE` on a `ClassICE` failure; the row
is written correctly; and the next launch ranks that same dry AZ first anyway.

**Observed.** `481723467561#g6e.12xlarge` held one row: `us-east-1a`, `last_success_at`
= 03:48Z. After writing a fresh ICE for it (Finding L2's workaround), a **new** remote create
(`sb-74999eaf`, dispatched 13:58Z) went straight back to `us-east-1a` and ICE'd again at
13:59:50Z, 13:59:59Z and 14:00:17Z. Removing the stale `last_success_at` attribute — leaving the
fresh ICE in place, so the AZ scores -1 — is what finally demotes it below the untried AZs
(score 0).

**Confirmed empirically.** A third create (`sb-17753fa7`) was dispatched with *only* that one
attribute removed — same profile, same link, same binary, same code path. It requested
**`us-east-1b`**:

```
time     : 2026-08-24T14:19:44Z
errorCode: Server.InsufficientInstanceCapacity
errorMsg : We currently do not have sufficient g6e.12xlarge capacity in the
           Availability Zone you requested (us-east-1b) ...
```

Three creates, one variable changed, AZ moved `1a -> 1a -> 1b`. That is the diagnosis confirmed
end to end: `rankScore`'s success short-circuit is what pinned every launch to the dry AZ.

**`km capacity` actively hides this.** Its verdict column and `rankScore` disagree: with both
attributes present the report prints

```
us-east-1a  yes  768 vCPU  2026-08-24T13:57Z  2026-08-24T03:48Z  recently-dry
us-east-1b  yes  768 vCPU  —                  —                  likely
```

— `us-east-1a` reads as `recently-dry` and `us-east-1b` as `likely`, while the ranker the create
path actually uses still puts `us-east-1a` first. An operator reading that table concludes the
sweep will avoid 1a. It will not. **This is the most dangerous part of the finding**: the
diagnostic tool and the decision logic are two different implementations that disagree, and the
one you can see is the one that is wrong.

**Suggested fix.** Evaluate freshness before stickiness — a fresh ICE is newer, more specific
evidence than an old success and should win:

```go
if entry.LastICEAt != nil && time.Since(*entry.LastICEAt) < freshICEWindow {
    return -1
}
if entry.LastSuccessAt != nil {
    return 2
}
```

Then reconcile `km capacity`'s verdict logic with `rankScore` so the report cannot disagree with
the ranker — ideally by having the report call `rankScore` rather than reimplementing the
judgement.

**Interaction with Finding L2.** The two defects compound and each masks the other. L3 pins
every launch to the dry AZ; L2 ensures the resulting ICE never returns to km, so the sweep
cannot advance to attempt 2 even though `maxAttempts` is 4 here (`spot: false` in the profile
sets the *substrate* to `ec2demand`, but the `--on-demand` **flag** was not passed, so the
`maxAttempts = 1` short-circuit at `create.go:1135` does **not** apply — rotation was permitted
and still never happened). Fixing only L2 leaves the ranker choosing the dry AZ first every
time; fixing only L3 leaves terraform burning 900s per attempt.

**One more scoping note.** The launcher role grants no `ec2:RequestSpotInstances` and no
`ec2:CreateFleet` (both verified `implicitDeny`), so a cross-account launch is on-demand-only.
Any future change that routes linked launches through the `--on-demand` flag would also trip
`create.go:1135` and pin `maxAttempts` to 1, removing AZ rotation entirely. Worth knowing before
someone "tidies up" that flag.

#### Finding L5 — a create killed mid-apply leaks its 300GB volume, `km destroy` does not reap it, and no doctor check sees it — **FIXED**

> **RESOLVED 2026-08-25.** New `checkLaunchAccountOrphanVolumes` reports unattached
> (`status=available`) volumes in every linked account whose `km:sandbox-id` is unknown to the
> home inventory, or absent. It surfaces the total GiB, because the wasted capacity is the cost
> signal an operator acts on.
>
> Deliberately **read-only**: it takes a new `LaunchAccountVolumeAPI` exposing only
> `DescribeVolumes`, rather than reusing `doctor_ebs.go`'s `EC2VolumeAPI` which also carries
> `DeleteVolume`. Reaping storage across an account boundary on a health check's say-so is an
> operator decision, and the narrow interface makes the wrong thing impossible rather than
> merely unwritten. A test asserts the interface cannot reach `DeleteVolume`.
>
> Boundary held: a volume belonging to a sandbox home still knows about is **not** reported —
> it may be mid-create or mid-teardown, and a check that cries wolf gets ignored.

Found 2026-08-24 during final cleanup. **This is the second occurrence** — `126-HANDOFF.md`
records that `sb-be0fdcb8`'s "orphan 300GB volume" was "removed by hand" — but the mechanism was
not identified then, so it recurred three more times in one session.

**What happened.** All three failed creates left a 300GB `gp3` volume behind in the target
account, `available` (never attached), correctly tagged, and **still present after
`km destroy <id> --remote --yes` reported success**:

| Volume | Created | AZ | `km:sandbox-id` |
|---|---|---|---|
| `vol-0104718db78af38e7` | 13:37:55Z | us-east-1a | `sb-ceffcb7c` |
| `vol-0a4fd8f56675df12e` | 13:59:33Z | us-east-1a | `sb-74999eaf` |
| `vol-0e732d3931df6d10e` | 14:19:15Z | us-east-1b | `sb-17753fa7` |

**Mechanism.** `aws_ebs_volume` is created *before* the `RunInstances` that then ICEs. The
create-handler Lambda is SIGKILLed at its 900s ceiling **mid-apply**, so terraform never
persists the state write. The volume exists in AWS but not in state — and `km destroy` operates
on state, so it destroys nothing and still exits 0. Every ingredient is a consequence of
Findings L2/L3: without the 900s kill there is no torn state, and without the dry-AZ pinning
there is no timeout.

**Why nothing catches it.**

- `km doctor`'s **`Untagged Available EBS Volumes`** check reported `no untagged available
  km-labeled EBS volumes` — truthfully, because these volumes *are* tagged. The check is scoped
  to *untagged* volumes, so a correctly-tagged orphan is invisible to it by design.
- The Phase 126 launch-account checks cover links, assumability, the artifacts grant, and orphan
  **instances** — there is **no orphan-volume check for a linked account**. Doctor reported all
  four green while 900GB of orphaned storage sat in the target account.

So the leak is silent in both directions: `km destroy` says success, `km doctor` says healthy.

**Cost.** 3 x 300GB gp3 at ~$0.08/GB-month is roughly **$72/month** had it gone unnoticed —
accruing in an account the home-side `km list` cannot see.

**Resolved for this session:** all three deleted after re-verifying each was `available` (never
`in-use`) and that its `km:sandbox-id` matched one of the three dead sandboxes. Target account
now holds zero instances and zero volumes.

**Recommended follow-up.** Extend the Phase 126 doctor group with an orphan-**volume** check for
linked accounts, mirroring `checkLaunchAccountOrphanInstances` but filtering
`status=available` + `tag:km:sandbox-id` against the home sandbox inventory. That is the check
that would have caught this, and it catches it in the home account too. Note it must not key on
*untagged*, which is the existing check's scope and the reason this slipped through.
