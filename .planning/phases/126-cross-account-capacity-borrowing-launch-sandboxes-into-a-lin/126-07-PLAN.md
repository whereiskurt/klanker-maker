## Verified precondition

The home artifacts bucket is created by Go code in the bootstrap flow — `ensureArtifactsBucket`
performs the bucket creation and versioning directly through the S3 API — and no Terraform
module in this repository declares a bucket policy for it. A read-modify-write of that
bucket's policy from Go therefore cannot be reverted by a later platform apply. Contrast
the mail bucket, whose policy IS Terraform-owned and carries an explicit comment that only
one policy resource may exist per bucket; that bucket must not be touched by this command.
The executor must re-confirm this before writing the policy code and record the confirmation
in the SUMMARY.

    `RunAccountRegister` runs with HOME account credentials. Sequence:
    1. Assemble the link record: read the fragment written by `km account add` when
       `--from-fragment` is given or the default fragment path exists; otherwise take every
       field from explicit flags. Fail clearly when neither source is complete.
    2. Load the home AWS configuration and validate credentials. Print the resolved account
       id, and fail when it equals the link's target account id.
    3. Write the external id into the home account's parameter store as an encrypted secure
       string at the path derived from the SSM prefix and the link name, with overwrite
       enabled. Record that path — and only that path — on the link record.
    4. Upsert the artifacts bucket grant via a read-modify-write: fetch the current policy
       (treating a no-such-policy error as an empty document), drop any existing statement
       carrying this link's identifier, append the new statement, and put the result back.

       the bucket's objects and list on the bucket itself; nothing else.

       cluster-style raw-map read-modify-write, preserving every other key in the file and
       writing at owner-only permissions.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| link fragment on disk → home account configuration and parameter store | the secret moves from the enrollment artifact into its runtime home |
| artifacts bucket policy → target account's box role | the single inbound cross-account data grant |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-126-35 | Information Disclosure | external id in km-config.yaml | high | mitigate | Only the parameter path is persisted to the configuration file; the value goes to an encrypted secure parameter. A test asserts the value's bytes do not appear in the written file. |
| T-126-36 | Tampering | cross-account write to the artifacts bucket | high | mitigate | The grant contains object-read and bucket-list actions only, asserted against the generated statement's action list rather than against source text, so a later edit that adds a write action fails the test. |
| T-126-37 | Tampering | bucket-policy clobbering | high | mitigate | Read-modify-write preserves every existing statement; the per-link identifier scopes both the upsert and the removal. The precondition that no Terraform module owns this bucket's policy is re-confirmed by the executor, and the Terraform-owned mail bucket is explicitly out of bounds. |
| T-126-38 | Elevation of Privilege | orphaned grant after removal | medium | mitigate | Removal is keyed by the same identifier helper the upsert uses, so a stale grant cannot survive a link's removal through an identifier mismatch. |
| T-126-39 | Denial of Service | half-finished teardown | medium | mitigate | When the target-account profile is absent, the command completes the home-side removal and prints the exact remaining command, rather than either failing entirely or pretending the footprint is gone. |
| T-126-40 | Repudiation | list leaking the secret | low | mitigate | The list output prints the parameter path only, asserted by a test. |
