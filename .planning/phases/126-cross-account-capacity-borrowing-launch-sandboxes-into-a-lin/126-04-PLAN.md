<objective>

bounded launcher role, the pre-baked box role with its permissions boundary, the
results bucket, and the optional lean network and EFS.

account and is therefore SCP-exempt — the blast-radius containment km normally gets

separated from the command that applies it.

  <action>
    Create the module directory and author the two roles.

    **Launcher trust policy.** IAM principal ARNs do not accept wildcards, so the spec's
    single illustrative principal line cannot be used literally. Build the trust policy
    from two variables:
    - `trusted_principal_arns` (list of strings, exact role ARNs) becomes an `AWS`
      principal list. The command in plan 05 populates it with the two deterministic
      account-A Lambda role ARNs — the create-handler role and the ttl-handler role, each
      named from the resource prefix in the trusting account — plus the operator's own
      role ARN when it can be resolved.
    - `trusted_principal_arn_patterns` (list of strings, default empty) is the escape hatch
      for a principal whose exact ARN is not knowable in advance, such as an IAM Identity
      Center role. When non-empty, add a SECOND statement whose principal is the trusting
      account's root and whose condition includes an `ArnLike` test on the request's
      principal ARN against those patterns.
    Both statements carry the same mandatory `StringEquals` condition on the STS external
    id. Add a variable `validation` (or a precondition) rejecting an empty external id —
    the confused-deputy protection must not be silently optional. Document in the module
    README that the account-root form delegates to account A's own administrator and is
    therefore broader than the exact-ARN form; the external id and the ARN patterns are
    what keep it narrow.

    **Launcher permission policy.** Reproduce the five statements from the spec, keeping
    the Sids so operators can correlate them with the simulate matrix:
    - launch-only: `ec2:RunInstances` on instance resources, conditioned on the instance
      type being in `var.instance_types`, on the required km managed-by request tag, and on
      the target subnet matching the km subnets. Because network provisioning now creates
      one subnet per AZ, the subnet condition must test membership in the full subnet ARN
      list, not equality against a single subnet.
    - supporting `RunInstances` resources: volumes, network interfaces, the km security
      group, the km subnets, images, key pairs.
    - pass-role: `iam:PassRole` restricted to the single pre-baked box role ARN and
      conditioned on the EC2 service, so the launcher never needs any role-creation
      permission.
    - tagged-only lifecycle: create-tags, terminate/stop/start instances, and
      create/attach/delete volume, all conditioned on the km managed-by RESOURCE tag.
    - read-only capacity check: EC2 describe actions plus the two Service Quotas read
      actions the GPU quota gate uses.
    Deliberately absent, and stated as such in a comment: any IAM write action, any
    Organizations action, any S3 action, and any action against another account.

    **Box role.** A pre-baked EC2 instance role with an instance profile. Its inline policy
    grants: SSM managed-instance core for shell and port-forward; read-only object access
    to account A's artifacts bucket via `var.artifacts_bucket_arn` (object-get only — no
    put, which is what makes the cross-account direction read-only); read and write on this
    account's own results bucket; and permission to read its own instance tags. Add the
    Bedrock model-invoke grant only when `var.enable_bedrock` is true, and comment that
    Bedrock traffic from a lean box in this account is unmetered by design.

    **Permissions boundary.** Create a managed policy that caps the box role's effective
    permissions to the same envelope, and attach it as the box role's
    `permissions_boundary`, so a later widening of the box role's own policy cannot escape
    it. State in a comment that this boundary is load-bearing precisely because this
    account is exempt from service control policies.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| account A principals → account B launcher role | the single cross-account door; account B is SCP-exempt so this role's policy is the whole boundary |
| launcher role → EC2 in account B | what the door can actually build |
| box role → account A artifacts bucket | read-only, the only inbound cross-account data path |
| account A principals → account B results bucket | read-only, the only outbound cross-account data path |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-126-15 | Elevation of Privilege | launcher permission policy scope | critical | mitigate | The launch statement is conditioned simultaneously on instance type, target subnet, and required request tags; lifecycle actions are conditioned on the resource tag; no IAM, Organizations, or S3 action is granted at all. Verified pre-apply by the eight-row simulate matrix in plan 10. |
| T-126-16 | Spoofing | confused deputy on AssumeRole | high | mitigate | Every trust statement carries the external-id condition, and the module rejects an empty external id rather than emitting a condition-free trust policy. |
| T-126-17 | Elevation of Privilege | account-root trust delegation | high | mitigate | The root-principal statement is opt-in (empty by default) and is always paired with both the external-id condition and an `ArnLike` principal-ARN condition. The README states plainly that this form delegates to account A's administrator. |
| T-126-18 | Elevation of Privilege | `iam:PassRole` scope | high | mitigate | Pass-role is restricted to the single pre-baked box role ARN and conditioned on the EC2 service, so the launcher cannot attach a more privileged role to an instance. |
| T-126-19 | Elevation of Privilege | box role widening | high | mitigate | The permissions boundary caps the box role's effective permissions independently of its own policy. There is no service-control-policy backstop in this account, which is exactly why the boundary is mandatory rather than defence-in-depth. |
| T-126-20 | Tampering | cross-account write | high | mitigate | The box role receives object-get only on account A's artifacts bucket, and account A's principals receive read-shaped actions only on the results bucket. A compromised box on either side can read across the boundary but never write. |
| T-126-21 | Information Disclosure | results bucket exposure | medium | mitigate | Bucket-owner-enforced ownership disables ACLs so access is policy-only; public access is blocked; the policy names exactly two principals. |
| T-126-22 | Denial of Service | single-subnet enrollment | medium | mitigate | One subnet per availability zone is provisioned and exported as a list, so the AZ-failover sweep retains more than one attempt where GPU capacity errors are worst. Re-provisioning later would require another privileged trip through account B. |
</threat_model>
