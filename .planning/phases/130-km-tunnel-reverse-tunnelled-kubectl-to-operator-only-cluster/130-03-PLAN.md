<objective>
Wire the `km tunnel` verb: render the three generated artifacts (box kubeconfig,
`km-kubetoken` shim, ssh argv), orchestrate the five legs, and expose the three
diagnostic flags.

Purpose: this is the plan that turns two testable libraries into a command. Its
riskiest content is the ssh argv — two options in it fail silently when absent —
and the orchestration ordering, since the SSM forward must be live before ssh runs
and must be torn down after it exits.

Output: `pkg/kubetunnel/render.go` with pure, fully-testable rendering; a Cobra
command in `internal/app/cmd/tunnel.go`; tests pinning the silent-failure options.
</objective>

  <name>Task 1: Pure renderers — box kubeconfig, km-kubetoken shim, provisioning script, ssh argv</name>

  </read_first>
  <behavior>
    - `RenderBoxKubeconfig` emits a kubeconfig whose server is `https://127.0.0.1:<bindPort>`, whose `tls-server-name` is Target.TLSServerName, and whose user exec command is `km-kubetoken` with apiVersion `client.authentication.k8s.io/v1`.
    - The rendered kubeconfig sets `current-context`, so a bare `kubectl` on the box works with no `--context`.
    - The rendered kubeconfig never contains the real cluster host as a `server:` value, only as `tls-server-name`.
    - `RenderShim` emits a `#!/bin/sh` script invoking `curl --unix-socket <sockPath>` and `exec`ing it so the exit code propagates.
    - `RenderShim` output contains no shell interpolation of untrusted values.
    - `BuildSSHArgs` always includes `-o ExitOnForwardFailure=yes` and `-o StreamLocalBindUnlink=yes`.
    - `BuildSSHArgs` includes `-R <bindPort>:<ServerHost>:<ServerPort>` and `-R <boxSock>:<localSock>`.
    - `BuildSSHArgs` includes `-i <keyPath>`, `-p <localPort>`, `sandbox@127.0.0.1`, and `-t` for the interactive form.
    - `BuildSSHArgs` in non-interactive (provisioning) form omits `-t` and both `-R` specs and instead carries the remote command.
    - `SSHCommandString` quotes arguments such that the output is copy-pasteable into a shell.
  </behavior>
  <action>
    Create `pkg/kubetunnel/render.go` holding only pure functions — no exec, no
    network, no filesystem. This is deliberate: it is the part of the command that
    can be fully verified from a machine with no VPN, no cluster, and no sandbox.

    `RenderBoxKubeconfig(t *Target, bindPort int) ([]byte, error)` marshals a
    kubeconfig via yaml.v3. Server is the loopback bind; the real hostname appears
    ONLY as `tls-server-name`. Set `current-context` to the context name.

    `RenderShim(sockPath string) string` returns the three-line shim. Use `exec` so
    curl's exit status becomes the shim's — kubectl distinguishes a plugin that
    failed from one that returned junk, and swallowing the code would turn a broker
    error into an unparseable-credential error.

    `BuildSSHArgs(opts SSHOpts) []string`. Both `-o` options are unconditional and
    are the single most important line in the phase: a failed `-R` bind is a
    WARNING by default, so without `ExitOnForwardFailure=yes` the operator gets a
    working shell attached to a dead tunnel. Add a comment saying exactly that, and
    pin both with the tests below.

    `SSHCommandString([]string) string` for `--print-ssh`, shell-quoting each arg.
  </action>

  </read_first>
  <behavior>
    - `--context` is required; omitting it errors before any AWS call.
    - `--dry-run` prints target, ssh argv, and box kubeconfig, and makes no AWS call and no network connection (verified with a fetcher stub that fails the test if called).
    - `--print-ssh` prints the interactive ssh command and exits 0 without connecting.
    - A local port already bound fails fast with a `--local-port` hint, before any AWS work.
    - A missing `~/.km/keys/<id>` fails with the same cross-machine hint vscode gives.
    - Default `--local-port` is 2223 and default `--bind-port` is 6443.
    - On a normal run the order is: resolve kubeconfig → pre-bind check → fetch sandbox → SSM forward up → broker listening → provisioning ssh → interactive ssh; a failure at any step tears down what was already started.
  </behavior>
  <action>
    Create `internal/app/cmd/tunnel.go` following the shape of `runVSCodeStart` —
    same fetcher/execFn seams so it is testable with stubs, same pre-bind probe,
    same key-path error text.

    Orchestration differs from vscode in one structural way worth a comment: vscode
    runs the SSM forward in the FOREGROUND as its last act, whereas this verb needs
    the forward live *underneath* an ssh session. Run `runReconnectingPortForward`
    in a goroutine with a cancellable context, wait for `sshBannerTunnelProbe` to
    report the port carrying traffic, then run ssh in the foreground; cancel the
    forward once ssh returns.

    Provisioning uses a second, non-interactive ssh over the same forward — NOT SSM
    send-command, which runs `dash` and mangles newlines on multi-line payloads.
    The remote script `mkdir -p ~/.km && chmod 700 ~/.km`, verifies `curl` exists
    (failing with an actionable message if not, since the shim depends on it),
    writes the kubeconfig and the shim via base64 to avoid quoting hazards, and
    `chmod +x` the shim.

    When ssh exits non-zero, print `tunnel dropped, re-run km tunnel` and return a
    non-zero error. Do not retry: reconnecting would lose the operator's shell state
    anyway, so faking resilience buys nothing and hides the real failure.

    Register the verb in root.go alongside vscode/desktop.
  </action>
