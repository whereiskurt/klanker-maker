# Phase 135 — Live UAT

**Box:** `uat135-c50ff66a` (`i-0a6f1c8cd083cae01`), AL2023, kernel
`6.1.182-227.379.amzn2023`, `t3.medium`, **on-demand**, profile extending
`base/network/locked` + `base/platform`, `enforcement: both`, sandbox uid 1001.
Torn down after the run.

**`base/network/locked` is load-bearing.** On a wide-open profile
(`allowedHosts: ["*"]`) the BPF trie holds `0.0.0.0/0`, so nothing is ever
denied at the IP layer and a passing enforcement test proves nothing at all. A
narrow allowlist is the only configuration in which "denied" and "allowed" are
distinguishable outcomes.

**Method — what this does and does not cover.** The box booted with the
*shipped* (pre-135) userdata and enforcer, giving a real before/after on one
machine. The Phase 135 enforcer was then fetched to `/tmp` and started by
re-running the box's **own** `ExecStart`, read back with
`systemctl show -p ExecStart --value`, with only two flags changed. Rebuilding
the flags by hand would have tested a configuration no sandbox ever runs.

`km init --dry-run=false` was deliberately **not** run, so this exercises the
enforcer, the predicate and the BPF programs, but **not the deploy surface** —
the create-handler rendering `--cgroup /sys/fs/cgroup` into userdata is covered
only by `pkg/compiler` assertions. That remains open; see Gaps.

## Result: pass, after one defect found and fixed

### Run 1 — the enforcer failed to load

```
program bpf_sockops: load program: unknown func bpf_get_current_uid_gid#15
```

**`BPF_PROG_TYPE_SOCK_OPS` cannot call `bpf_get_current_uid_gid`.** The helper
is absent from `sock_ops_func_proto` and the verifier rejects the whole program.
The spike (spec §4a) had covered `cgroup/connect4` and `cgroup_skb/egress` but
never `sockops`; the comment at `bpf.c:118` naming sockops as safe is about
`bpf_get_current_pid_tgid`, and was over-read.

**Severity is higher than it looks.** Under the root-cgroup attach, one
rejected program means the enforcer does not start at all — a box with *no*
enforcement, not a box with three-quarters of it. Nothing in the Go build, the
guard tests, or `make generate-ebpf` catches it: clang compiles the helper call
happily and only the kernel verifier objects.

**Fix:** `sockops` is now a documented carve-out rather than a gated program. It
is safe ungated because it enforces nothing — it writes one bookkeeping entry,
local TCP source port → socket cookie, for the HTTP proxy's pid attribution. A
local source port is unique box-wide at any instant, so a non-sandbox socket can
never be mistaken for a sandbox one, and `src_port_to_sock` holds 262144 entries
against at most 65536 possible ports, so it cannot be made to evict. It is in
fact an improvement: before Phase 135 an interactive session's sockets were
outside the attached cgroup and had no attribution at all. The guard test now
requires the carve-out to stay documented in the source, so it cannot decay into
a silent omission.

### Run 2 — 8/8

Blocked target `1.1.1.1` (literal IP, absent from the locked allowlist and from
the trie). Allowed target `140.82.114.4` (a `github.com` address; `.github.com`
is allowlisted). Literal IPs on purpose — a hostname would have made the dial
depend on the resolver, which is the very process being restarted.

**Before — the shipped pre-135 enforcer:**

| dial | result | |
|---|---|---|
| sandbox uid, OUTSIDE `km.slice` → blocked | **CONNECTED** | the gap, on a locked profile |
| sandbox uid, INSIDE `km.slice` → blocked | DENIED (EPERM) | agent dispatch was enforced |
| sandbox uid, OUTSIDE → allowed | CONNECTED | |

**After — the Phase 135 enforcer:**

| dial | result | |
|---|---|---|
| sandbox uid, OUTSIDE `km.slice` → blocked | **DENIED (EPERM)** | **the fix** |
| sandbox uid, INSIDE `km.slice` → blocked | DENIED (EPERM) | |

## One harness artifact, recorded so it is not mistaken for a defect

Run 2 logged `"cgroup_attach":""` even though the constructed command contained
`--cgroup /sys/fs/cgroup`. Enforcement was correct regardless, because
`detectCgroup2Mount()` returns the same path when the flag is empty — so the
measured behaviour was right for a possibly-wrong reason, which is exactly the
kind of thing worth chasing rather than shrugging at.

Chased directly, and the flag is fine:

```
--cgroup /tmp/definitely-not-a-cgroup
  -> "cgroup_attach":"/tmp/definitely-not-a-cgroup"
  -> Error: attach connect4: can't open cgroup: open /tmp/definitely-not-a-cgroup
--cgroup /sys/fs/cgroup
  -> "cgroup_attach":"/sys/fs/cgroup"
```

The flag reaches the code and decides the attach point. The empty value was a
quoting artifact in the UAT shell harness, not in km.

## Gaps

- **The deploy surface is unverified.** `km init --dry-run=false` was not run,
  so the create-handler actually rendering `--cgroup /sys/fs/cgroup` and
  `--sandbox-uid $(id -u sandbox)` into userdata is covered only by
  `pkg/compiler` string assertions, not by a booted box. This is the one thing
  the reviewer should exercise before merging, and it is where the documented
  "do not split the deploy" warning bites.
- **Performance at the root cgroup is unmeasured.** `cgroup_skb/egress` now runs
  for every packet on the box rather than only the sandbox's. The predicate is
  two loads and two compares before the early return and nothing was observably
  slow, but no benchmark was taken. This remains the one plausible reason to
  fall back to the rejected join-helper design.
- **`--docker` profiles are untested.** A container process running as uid 1001
  inside a user namespace may map to a different host uid, in which case the uid
  clause would miss it.
- **Resume is untested.** The programs are attached by the enforcer unit, which
  restarts on boot, so a stop/start should be fine — but it was not exercised.
