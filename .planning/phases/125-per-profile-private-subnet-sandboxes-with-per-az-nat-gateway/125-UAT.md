### Step 8 — NEGATIVE — FAIL, then FIXED, then PASS

**DEFECT 3 FOUND HERE — the most serious of the phase.**

First run, with NAT off: `km create profiles/private-subnet.yaml --alias privfail` returned
**exit 0** and provisioned `priv-e8e27350` at `10.0.101.109` into a private subnet whose route
table had no default route. The box had **no egress at all**, never registered with SSM
(`describe-instance-information` returned empty), and was therefore completely unmanageable —
no `km shell`, no `km agent` — while still billing. Exactly the state the guard exists to
prevent. It was destroyed immediately.

Root cause: `checkPrivateSubnetGuard` tested `len(privateSubnets) > 0`. That is **always
true** — the private subnets exist unconditionally and survive as routeless islands when NAT
is off, which is the very property Step 7 verifies. The guard was dead code. Both call sites
(`runCreate` and `runCreateRemote`) were correctly wired and both were reached; the defect was
purely *which slice they passed*.

Fixed in commit `d92dbc93`: the guard now takes `networkOutputs.NATGatewayIDs`, which is empty
exactly when the install has no egress path for private subnets.

Re-run after the fix — **PASS**, verbatim:

```
Error: profile requests spec.network.privateSubnet but this install has no NAT gateway — set network.nat_gateway: true in km-config.yaml and run 'km init --dry-run=false' first
```

Exit 1, before any artifact write: no `{prefix}-sandboxes` row for `priv-ec5f9e54`, no
instance, no sandbox directory.

**Note on test coverage:** the guard's unit tests passed both before and after this fix. The
pure function was always correct — the defect was in the caller's argument. A table test over
the helper structurally cannot catch this class of bug, so a wiring-assertion regression test
was added alongside the fix.

### Spot-checks

- `km doctor` after Step 2 (NAT up, no private sandbox yet): **PASS** —
  `⚠ NAT gateway idle  network.nat_gateway is enabled but no private sandbox depends on it —
  you are paying about $132/month (4 AZs) ... safe to disable`, with remediation.
- `km doctor` after Step 3 (NAT up, private sandbox RUNNING): **FAIL, then FIXED, then PASS.**

  **DEFECT 2 FOUND HERE.** The check still reported "no running private sandbox depends on
  it — safe to disable" while `priv-913ff0f3` was live on `10.0.101.83` egressing through
  `nat-0dc28e8f9fb164acb`. Root cause: `runningPrivateSandboxIDs` required
  `m.Status == "running"`, but `km create` never writes a `status` attribute to the
  `{prefix}-sandboxes` row — `km list` derives status by reconciling against live EC2. The
  field was always empty, so the filter matched nothing. The failure direction was dangerous:
  an operator following the remediation would have torn down the NAT their running sandbox's
  egress depended on. Fixed fail-safe in commit `fa43cf4f` — a private row counts as
  NAT-dependent unless its status is definitively terminal (`failed`); rows are deleted on
  destroy (Phase 109), so a present row means the sandbox exists, and `stopped`/`starting`/`""`
  all count since a stopped private sandbox needs NAT again the moment it resumes. Two unit
  tests had asserted the old behaviour and were codifying the bug; both corrected.

  After the fix, verified live: `✓ NAT gateway idle  network.nat_gateway enabled; 1 private
  sandbox(es) depend on it`.

- `km doctor` after Step 7 (NAT torn down): **PASS** — both checks quiet:
  `- NAT gateway idle  network.nat_gateway not set — NAT off` and
  `- Private sandboxes without NAT  no running private sandboxes — nothing to check`.
