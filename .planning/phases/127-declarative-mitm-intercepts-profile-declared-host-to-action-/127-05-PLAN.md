    Write `docs/mitm-intercepts.md` covering, in an order that reads for an operator:

    What the block is and the worked YAML for both action forms. The default: opt-in, off,
    and the explicit statement that the previously-unconditional built-in behaviour stops
    on the next `km create` — this is the one place the repo departs from its usual
    dormant-equals-byte-identical rule, and it is deliberate.

    How to get the old behaviour back: one `extends:` line naming the fragment, pointing at
    `profiles/mitm-demo.yaml` as the worked example.

    The override rule: intercepts resolve by `name`, last-wins, WHOLE ENTRY. `name` plus
    `enabled: false` switches an inherited rule off; an override that keeps a rule enabled
    must restate `hosts` and `action` because there is nothing left to inherit them from.
    Say why the whole-entry rule was chosen over a field-level merge — a field merge would
    union `hosts` under Phase 117 semantics, so a leaf could never narrow an inherited host
    list. Note that a disabled rule is dropped at compile time and never reaches the box.

    Host matching: case-insensitive, port stripped, exact by default, leading dot matches
    the apex and any subdomain, no regex, and no `*` wildcard. Call out the narrowing
    explicitly as a bug fix: the old pattern was unanchored at the end, so a host formed by
    appending an attacker-controlled suffix to the declared host was also intercepted; the
    new matcher rejects it.

    Precedence: the deny gate first, then the Bedrock / Anthropic / OpenAI metering
    handlers and the GitHub repo filter, then operator intercepts, then the general
    allowlist. State the consequence in both directions — a rule naming a metering host is
    dead, and a rule for a host that is NOT on the allowlist still fires, which is the
    useful case for serving a canned error on a host you do not allow.

    Why there is no `block` action: `spec.network.egress.deniedHosts` already blocks with
    strictly stronger semantics — ahead of everything, broader subdomain matching, and
    runtime-appendable via `km-netpolicy`. Link to `docs/egress-deny-lists.md`.

    The three `km validate` warnings, each with the fix, and the five errors.

    eBPF and both: intercept hosts are threaded into the proxy-host list so `connect4`
    DNATs them, but DNS is deliberately not widened — a host outside `allowedDNSSuffixes`
    never resolves and the rule silently never fires, which is what the third warning is
    for. Also record the transparent-path asymmetry from plan 02: the relay dials and
    handshakes the real destination before inspecting, so an intercept for an unreachable
    host cannot fire under DNAT even though it can on the explicit-proxy path.

    Deploy surface, stated as a single sequence: `make build` + `make build-lambdas` +
    `km init --dry-run=false`. All three, because three things land together — the sidecar
    binary, the profile schema field the create-handler's bundled `toolchain/km` validates,
    and the user-data drop-in the create-handler zip renders. State plainly that
    `km init --sidecars` alone is not merely insufficient but actively harmful mid-rollout:
    the new binary has no rule set to read, so a sidecar-only refresh drops the built-in
    behaviour on a live box while the profile still cannot declare it back. Note that no
    Terraform module, DynamoDB table, IAM policy, Lambda bridge or SES resource changes,
    that user-data goldens are untouched in the dormant case, and that existing sandboxes
    keep today's behaviour until `km destroy && km create`.

    A short "not available" section naming the three deferred items — runtime mutation,
    `respond.fromFile`, and request/response rewriting — so nobody goes looking.
