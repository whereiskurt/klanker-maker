## Deploy preamble (read before running any live step)

Run, in this exact order:

```bash
make build
make build-lambdas
km init --dry-run=false
```

**`km init --sidecars` alone is not merely insufficient — it is actively harmful mid-rollout.**
It rebuilds and uploads the sidecar binaries but does NOT refresh the create-handler zip that
renders the `mitm.conf` user-data drop-in. Running `--sidecars` alone drops the built-in Rickroll
on a live box (the new `km-http-proxy` binary has no `KM_MITM_INTERCEPTS` to read) while leaving
the profile schema unable to declare it back until the full sequence completes. See
`docs/mitm-intercepts.md` § Deploy surface.

**Existing sandboxes keep today's behaviour until `km destroy && km create`.** Every step below
therefore needs a **freshly created** box — an already-running sandbox will not pick up either
the new opt-in default or the demo profile's rules.

### Deploy incident — provider lock drift (resolved)

The first `km init --dry-run=false` **failed** on the last module (`ses`) with:

```
locked provider registry.terraform.io/hashicorp/aws 6.61.0
does not match configured version constraint 6.46.0
```

27/28 modules had already applied, including `create-handler` and the `km-http-proxy`
sidecar + `toolchain/km` uploads. The stale `6.61.0` pin lived in **three** places and all
three had to be swept — clearing only the first two reproduced the failure:

1. `infra/modules/ses/v2.0.0/.terraform.lock.hcl` and
   `infra/modules/ses-shared-rule-set/v1.0.0/.terraform.lock.hcl` (module-source strays,
   untracked + gitignored)
2. `infra/live/use1/ses/.terraform.lock.hcl` (live unit lock, freshly written by the failed
   run and seeded from the strays)
3. `infra/live/use1/ses/.terragrunt-cache/**/.terraform.lock.hcl` (the cache copy — this one
   survived steps 1–2 and re-poisoned the retry)

After the sweep, `ses` planned `0 to add, 1 to change, 0 to destroy` and applied cleanly.

**Reporting trap worth recording:** the run was launched as
`km init … > log 2>&1; echo "INIT_EXIT=$?" | tee -a log`, and the *harness* reported
"exit code 0" — that was `tee`'s status, not `km init`'s. The log's own `INIT_EXIT=1` was the
truth. Same failure mode as [[feedback_check_go_test_exit_not_pipe]], one layer further out.

### Methodology trap — `sudo -u` is not a login shell (INVALIDATED THE FIRST RUN)

The first pass of Steps 1/2/4 was run with `sudo -u sandbox curl …` and produced a
**false negative**: the demo box returned Google's real `HTTP/2 200` and looked like the
intercept had not fired.

Cause: the proxy is reached via `HTTPS_PROXY=http://127.0.0.1:3128` exported from
`/etc/profile.d/`. `sudo -u` does **not** start a login shell, so the variable was absent and
curl egressed directly, bypassing the proxy entirely. Neither box had any iptables DNAT rules
(`nat DNAT rule count: 0` on all three), so nothing else forced the traffic back.

**Every result below was re-run with `sudo -iu sandbox bash -lc '…'`** (login shell) and
cross-checked with an explicit `--proxy http://127.0.0.1:3128`. Both forms agree.

Corollary for the runbook: `km shell <id> -- <cmd>` (used in the original draft of this
document) is **not supported** — `km shell` accepts exactly one argument. Non-interactive
probes must go through `aws ssm send-command`, base64-wrapping the payload because
`AWS-RunShellScript` executes `/bin/dash`, not bash.
