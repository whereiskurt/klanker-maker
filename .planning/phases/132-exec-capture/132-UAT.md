# Phase 132 — live UAT: exec capture (`km-netpolicy execs | who | execs save`)

**Status: NOT YET RUN.** Phase 132 ships code-complete with live UAT pending.

Everything through Task 9 is proven by unit tests, including a cross-compiled
`linux/amd64` run of the BPF programs under Docker (see
`docs/superpowers/specs/2026-08-29-exec-capture-design.md` §7). What no unit
test can reach is a real kernel loading four tracepoints alongside the eBPF
enforcer's cgroup programs and SSL uprobes, a real agentic workload generating
the trace, and the EC2 stop/pause/terminate lifecycle. This checklist is that.

Steps 1–7 are the design's own §8 list, run against a genuinely agentic
workload — VulnHunter scanning `defcon.run.34` — chosen because it is
subprocess-heavy in a way no synthetic test reproduces. Steps 8–10 are the EC2
lifecycle checks; they are the reason this phase is EC2-only in practice, and
the most likely place for something to interact badly with everything else
already loaded onto this kernel.

```bash
systemctl is-active km-ebpf-enforcer km-execlog
```

as the sandbox user with a login shell, not as root** — Step 1's `km shell
--root` is for reading the exec store, but a probe run as root bypasses both
the uid-0 iptables RETURN and the sandbox cgroup, so an allowed-host connect
would pass trivially and `evil.example.com` would only fail because the on-box
resolver NXDOMAINs for root too — DNS doing the work, not the enforcement path
this step exists to prove is unharmed by the new tracepoints. `sudo -u
sandbox` alone is not enough either: it skips the profile that sets
`HTTPS_PROXY`, so the request egresses direct and gives a false negative
(the tell is HTTP/2 on the response — that means you bypassed the proxy and
this result cannot be trusted). Use `sudo -iu` for a real login shell:

```bash
sudo -iu sandbox bash -lc 'curl -sS -o /dev/null -w "%{http_code} %{http_version}\n" https://<a host on the allowlist>/'
sudo -iu sandbox bash -lc 'curl -sS https://evil.example.com/ ; echo "exit=$?"'
```

**Expect:** the allowed host connects (and reports **not** HTTP/2 — HTTP/2
means the proxy was bypassed); `evil.example.com` is blocked (times out or is
refused, per the profile's enforcement mode).

This is the load-bearing check of the step: km now loads cgroup BPF programs,
SSL uprobes, **and** four exec/exit tracepoints on one kernel. That
combination has never been run before this UAT. If a box also extends
`base/security/wiz`, repeat this check there too — the sensor adds its own
kprobes, and this phase's own design doc calls that the single most likely
place for an interaction nobody has seen yet.

## What it found — three defects, all in pre-existing code

None of these were reachable by code review; each needed a real kernel.

### UAT-1 — `who` could not attribute anything (fixed)

Symptom: no flow record on the box carried a pid, and no `flows.ebpf.jsonl`
existed at all. Two independent causes, both confirmed by measurement:

**(a) Agent traffic was never in the enforcement cgroup.** cgroup v2 only permits
migration by a process that can write the *common ancestor's* `cgroup.procs`,
which is root-owned — so the self-migration at every enrollment site had been
failing silently behind `2>/dev/null || true`. Measured:

| launch context | cgroup | in scope |
|---|---|---|
| `km-session-entry` → `km-sandbox-shell` | `km.slice/km-<id>.scope` | yes |
| `sudo -u sandbox bash -lc` (poller path) | `user.slice/…/session-c7.scope` | no |
| `su - sandbox` | `user.slice/…/session-c8.scope` | no |

Joining the cgroup *before* `sudo` does not work either — PAM/logind migrates the
process straight back. `setpriv` and `runuser` both preserve it. Fixed in
`0825b8ed` across 15 dispatch sites (Slack ×3, GitHub ×4, HackerOne ×4,
Webhook ×2, `km-queue-runner` ×1), joining as root in a subshell and dropping with
`runuser`, so the poller itself stays outside the cgroup and its SQS calls stay
unfiltered.

**Consequence beyond this phase:** the eBPF `connect4`/`egress` programs had
therefore been inert for agent traffic. What actually enforced was the DNS
resolver plus the HTTP proxy. This fix switches that enforcement on.

**(b) Proxied traffic emits no eBPF event at all.** The sandbox user has
`HTTPS_PROXY=http://127.0.0.1:3128`, so the agent reaches the proxy *explicitly*
and `connect4` only ever sees a loopback connect — neither a deny nor a redirect.
Measured from inside the cgroup: proxied → no row; same request with the proxy env
unset → row with `pid` and `comm`. So the pid has to come from the HTTP proxy.
Fixed in `53762681`: `socket_pid_map` is now pinned (it never was), and the proxy
resolves source port → cookie → pid through it and `src_port_to_sock`, stamping
all 17 flow-write sites via one chokepoint. Fails soft everywhere — absent pins
(pure `proxy` mode has no BPF), a miss, or an error costs a pid, never a request.

### UAT-2 — manual `execs save` fails with no environment (open)

`km-netpolicy execs save` run by hand exits with `KM_ARTIFACTS_BUCKET is not set`.
The systemd unit supplies it, so `ExecStopPost` works — but `docs/exec-capture.md`
tells operators to run the verb manually, and that path has none.
`/etc/km/netpolicy.env` carries `KM_FLOWLOG_DIR` and its siblings but neither
`KM_ARTIFACTS_BUCKET`, `KM_SANDBOX_ID` nor `KM_EXEC_DIR`. Reading them via
`os.Getenv` matched `uploadCapture`'s precedent, which is right for a daemon and
wrong for an operator verb. Fix is to route them through `buildOpts`' `pick()`
(env → `/etc/km/netpolicy.env`) or to write them into that file in userdata.

### UAT-3 — every eBPF flow record had a byte-reversed IP and port (fixed)

`curl https://github.com/` recorded as:

```json
{"src":"ebpf","verdict":"redirect","addr":"3.114.82.140","port":47873,"pid":33061,"comm":"curl"}
```

`47873` = `0xBB01`; `443` = `0x01BB`. `3.114.82.140` reversed is `140.82.114.3`,
inside GitHub's `140.82.112.0/20`. The ring-buffer decode is little-endian, so
re-encoding the address big-endian double-reversed the wire bytes. Fixed in
`d36a727b`.

**Only `connect4` needs the port swap.** `sendmsg4` (`bpf.c:266`) and the
`egress_skb` path both call `bpf_ntohs` before emitting, so swapping those would
turn every DNS-redirect flow's port 53 into 52021 — a new bug in the one flow type
that is always present. Pinned by `TestHandleEvent_Sendmsg4PortNotDoubleSwapped`.

This corrupted the Phase 131 census and the `ebpf_network_deny` audit log too, not
just the new verb.

# `who` verified end to end — 2026-08-30

After the four post-UAT fixes, re-run on `deny-e360150b` (`t3.medium` spot,
`enforcement: both`, built from `km` + `http-proxy` sidecars carrying the fixes):

```
$ km-netpolicy who github.com
15:18:03  redirect http  github.com  ← pid=31946 curl -sS -o /dev/null -w … https://github.com/
```

Corroborated independently by the exec trace — same pid, recorded 6 ms before the
flow:

```json
{"ts":"2026-08-30T15:18:03.498309886Z","kind":"exec","pid":31946,"ppid":31578,
 "uid":1001,"comm":"curl","args":["curl","-sS","-o","/dev/null","-w",
 "github.com -> %{http_code}\\n","https://github.com/"],"ret":0,"cgroup_id":4758}
```

A second, independent request attributed on an **`allow`** verdict rather than a
redirect — the case that was impossible before, because the eBPF ring buffer
never emits for an allowed connection:

```
$ km-netpolicy who nodejs.org
15:19:17  allow http  nodejs.org  ← pid=32451 curl -sS -o /dev/null -w … https://nodejs.org/
```

Port renders as `443`, not `47873` — the endianness correction holding on a real
box.

## What made it work — four fixes, in dependency order

1. **`connect4` records the pid before its exemptions** (`e4430bb0`). The sandbox
   reaches the proxy at `127.0.0.1:3128`, and `connect4` returned at the
   localhost exemption *before* populating `socket_pid_map` — so the proxy was
   looking up precisely the sockets that were never recorded. The map is now
   `LRU_HASH`, because it has `max_entries 10000`, no deletion path anywhere, and
   the reordering adds every loopback connect; a plain hash would have filled and
   then failed silently on insert.
2. **`socket_pid_map` is pinned** (`53762681`). It was absent from the enforcer's
   explicit `mapsToPin` list, so the proxy could not open it at all.
3. **The HTTP proxy resolves and stamps the pid** (`53762681`), source port →
   `src_port_to_sock` → cookie → `socket_pid_map` → pid, at all 17 flow-write
   sites through one `recordFlow` chokepoint. Fails soft everywhere.
4. **Agent processes are actually in the enforcement cgroup** (`0825b8ed`), via a
   root-side join plus `runuser`. Without this `connect4` never runs for agent
   traffic and none of the above has any input.

## Rows that remain unattributed, and why that is correct

`resolver`-sourced rows carry no pid, and never will — the DNS resolver answers a
query, it does not own the connecting socket. Rows recorded before a process
entered the cgroup are likewise unattributable. Both print an explanation rather
than `(none)`.

## Step 10 — BPF coexistence: PASS

Enforcer, exec tracer, HTTP proxy and DNS proxy all `active` simultaneously. All
four cgroup links and all four maps pinned, including `socket_pid_map`.
Enforcement still correct, probed **as the sandbox user inside the cgroup**
(root bypasses the DNAT and would pass trivially):

```
ALLOWED github.com        -> 200 h1.1
DENIED  evil.example.com  -> exit=56  (Proxy CONNECT aborted)
```

`h1.1` matters: HTTP/2 on the allowed host would mean the request bypassed the
proxy and the result could not be trusted.

## Step 8 — stop/resume: PASS, with one case still untested

Trace survived a full stop/resume cycle: 11,139 → 13,077 records, the pre-stop
marker still present, the tracer active again afterwards, and the newest record's
timestamp inside the same second as the host clock — no boot-offset skew.

**Still untested:** true hibernation. `deny-layered` has no `hibernation: true`,
so `km stop`/`km resume` is a reboot — the daemon restarts and recomputes its
clock offset from scratch. The case `wallTimeOf` was actually designed for (a
process running continuously across a suspend and an NTP correction) needs a
hibernation-enabled profile.

**Also learned:** a **spot** sandbox cannot be resumed after `km stop` —
`IncorrectSpotRequestState`. Use `--on-demand` for any stop/resume testing.

## Step 9 — a real shutdown: FAILED, root-caused, fixed, re-verified

The first run failed. `ExecStopPost` ran but its upload died:

```
km-netpolicy execs save: upload failed, trace kept locally at /var/lib/km/execs/execs.jsonl:
  operation error S3: PutObject … dial tcp: lookup km-artifacts-12345.s3.us-east-1.amazonaws.com
  on 127.0.0.1:53: read udp …->127.0.0.1:53: read: connection refused
km-execlog.service: Failed with result 'exit-code'.
```

**Cause.** Under `ebpf`/`both`, `/etc/resolv.conf` points at the resolver that
`km-ebpf-enforcer.service` provides. systemd stopped that enforcer before
`km-execlog`'s stop hook, so the S3 hostname could not resolve. `km-execlog`
declared only `After=network-online.target`, which orders it against the network
but not against the unit that actually answers DNS on this box.

This is exactly why the substitute test was not enough: `systemctl stop` on a
running box passes, because the resolver is still alive. Only a real shutdown
orders the enforcer down first.

**Fixed** in PR #94 — `After=km-ebpf-enforcer.service km-dns-proxy.service`, so
systemd (which stops units in reverse `After=` order) stops the tracer while DNS
still resolves; plus `ExecStopPost=-…`, so a best-effort upload failing no longer
leaves the unit `Failed`.

**Re-verified on a box carrying the fix.** A prefix holding one object from a
manual save gained a second, written during the ACPI shutdown:

```
14:51:20  1,555,996  execs-20260830T185119Z.jsonl   ← manual `execs save`
14:51:50  1,679,838  execs-20260830T185149Z.jsonl   ← ExecStopPost, during shutdown
```

The shutdown-written object is larger — it captured the shutdown's own execs.

its own, because `/etc/km/netpolicy.env` never carried the keys; userdata now

Verified from a root login shell:

```
saved: s3://km-artifacts-12345/execs/deny-4d16e4b7/execs-20260830T185119Z.jsonl (1555996 bytes)
```

## Step 9 on the TERMINATE path: FAILS — `km stop` and `km destroy` are not equivalent

Re-run on an on-demand sandbox (`deny-a38b017a`) carrying the #94 fix, with an
empty `execs/` prefix and a 1,672,598-byte local trace before teardown:

```
$ aws s3 ls s3://…/execs/deny-a38b017a/     # before: empty
$ km destroy deny-a38b017a --yes
… instance: running -> shutting-down -> terminated
$ aws s3 ls s3://…/execs/deny-a38b017a/     # after: STILL EMPTY
```

The same box's ordering was confirmed in effect first — `After` resolved to
`km-ebpf-enforcer.service` and `km-dns-proxy.service`, and `ExecStopPost` was
dash-prefixed.

**So #94 fixes `km stop` and does NOT cover `km destroy`.** That was assumed
equivalent on the reasoning that both drive an ACPI shutdown; the measurement
says otherwise. Plausible causes, none yet confirmed: `TerminateInstances` gives
a shorter grace window than `StopInstances`, and/or `terraform destroy` removes
the instance's networking (SG/ENI/route) alongside it, so the upload has no path
out even though DNS resolves.

**Why this matters more than the stop case.** `km destroy` is the normal end of a
sandbox's life; `km stop` is the exception. The automatic save therefore does not
fire on the teardown operators actually use, and the trace dies with the volume.
`docs/exec-capture.md` should not promise a save on shutdown without this
qualification.

**Not a regression** — this never worked; the first run failed on DNS and this one
fails for a different reason. #94 is still correct and still needed for `km stop`.

**Candidate fix, not yet attempted:** have the destroy path save before it tears
anything down — an SSM `execs save` from `km destroy` and from the ttl-handler's
expiry path, before `terraform destroy` runs. That does not depend on the
shutdown window at all, which is what makes it likely to work where `ExecStopPost`
cannot.

## Step 9 on the TERMINATE path, second attempt: PASS

The candidate fix above was built (#96) and, on its first live test, **did not
work either** — a `km destroy` against `deny-404262a8` left the prefix empty
before and after. The hook was correctly wired and firing; the save it invoked
was failing on the box.

**The cause was a third missing piece of the same environment.** `km-netpolicy
execs save` resolves its bucket, sandbox id and store directory from the
environment, falling back to `/etc/km/netpolicy.env`. That file carried three
keys and not the fourth: `AWS_REGION`. An interactive root login inherits a
region from `/etc/profile.d`, so every documented path worked — but SSM's
`AWS-RunShellScript` runs a **bare, non-login shell**, which sources none of
it. The verb died on `Invalid region: region was not a valid DNS name`, an
error that reads like a bucket problem.

This had been observed and written down a day earlier, under `env -i`, and
dismissed in the same breath: *"not a defect on any documented path."* That was
true when it was written. #96 made SSM a documented path and turned it into the
defect that broke the feature.

**Why nobody saw it fail.** `runDestroy` replaces the global logger with
`io.Discard` unless `--verbose` is passed. The failure was reported at `Warn`,
into a logger that does not exist on the default path. Fixed in #97 by printing
to stderr as well — a best-effort operation still has to be able to say it
failed.

**Fixed in #97**, three ways, because the binary and the userdata that renders
`netpolicy.env` ship on different cadences: userdata writes `AWS_REGION` into
the file; `execs save` resolves it through `opts` like every other value; and
the SSM command sources `/etc/km/netpolicy.env` into its own environment first,
so the fix does not depend on which half of the pair a given box has.

**Verified live on `deny-295f2666`** (on-demand, created after `make build` +
`km init --sidecars` so it carries both halves). The box was confirmed to carry
`AWS_REGION=us-east-1` in `netpolicy.env` first. Then the precise failure vector
was reproduced with a genuinely empty environment:

```
$ env -i /opt/km/bin/km-netpolicy execs save
saved: s3://…/execs/deny-295f2666/execs-20260830T202929Z.jsonl (1660636 bytes)
```

and then the real thing:

```
16:29:30  1,660,636  execs-20260830T202929Z.jsonl   ← the env -i save above
16:30:31  1,688,763  execs-20260830T203030Z.jsonl   ← written during km destroy
$ aws ec2 describe-instances … --query '…State.Name'
terminated
```

The destroy-written object is 28KB larger than the one taken a minute earlier:
it captured the destroy's own execs, which is what proves it ran on the box
during teardown rather than being a copy of something already uploaded.

**Three measurements, three different failures, one working path.** DNS
ordering, then a missing destroy-time save, then a missing region. Each was
found by listing an S3 prefix, and each had survived reasoning that sounded
correct — including, twice, my own.
