# Phase 132 — live UAT: exec capture (`km-netpolicy execs | who | execs save`)

**Status: NOT YET RUN.** Phase 132 ships code-complete with live UAT pending.

Everything through Task 9 is proven by unit tests, including a cross-compiled
`linux/amd64` run of the BPF programs under Docker (see
`docs/superpowers/specs/2026-08-29-exec-capture-design.md` §7). What no unit
test can reach is a real kernel loading four tracepoints alongside the eBPF
enforcer's cgroup programs and SSL uprobes, a real agentic workload generating
the trace, and the EC2 stop/pause/terminate lifecycle. This checklist is that.

Steps 1–7 are the design's own §8 list, run against a genuinely agentic
workload — VulnHunter scanning `defcon.run.34` — chosen because it is
subprocess-heavy in a way no synthetic test reproduces. Steps 8–10 are the EC2
lifecycle checks; they are the reason this phase is EC2-only in practice, and
the most likely place for something to interact badly with everything else
already loaded onto this kernel.

## Step 6 — rotation stays sane under volume, `--since` stays responsive

Generate enough execs to force rotation (16 MiB cap) — a tight loop of a
trivial command is fine for volume purposes:

```bash
for i in $(seq 1 5000); do /usr/bin/true; done
```

Then:

```bash
km-netpolicy execs --since 10m | wc -l
cat /var/lib/km/execs/execs.jsonl.rotations
```

**Expect:** `execs --since 10m` returns promptly (no multi-second hang) and a
plausible count; `.rotations` reports a count `>= 0` that increases as the
loop is repeated past the 16 MiB cap. If it reaches `2`, confirm
`km-netpolicy execs` now prints the rotation warning to stderr (see

## Step 8 — pause/resume keeps the trace and keeps its timestamps sane

```bash
km pause "$SANDBOX"
km resume "$SANDBOX"
```

Once resumed, run one fresh command inside the sandbox, then:

```bash
km-netpolicy execs --since 5m
```

**Expect:**
- [ ] The pre-pause trace is still present (`/var/lib/km/execs` is on the EBS
      root volume, so hibernation must not lose it)
- [ ] The fresh post-resume command appears
- [ ] Its timestamp is near **wall-clock now**, not skewed by however long the
      box was paused — this is exactly what `wallTimeOf` (converting the
      kernel's `CLOCK_BOOTTIME` stamp against wall time at read time, not at
      boot time) exists to get right. A stale boot-instant bug would fail
      exactly here and nowhere else a unit test could reach.

## Step 9 — a real terminate saves

On a box with a non-empty trace:

```bash
km destroy "$SANDBOX" --remote --yes
```

Wait for the instance to actually terminate (`km list` no longer shows it, or
`aws ec2 describe-instances` confirms `terminated`), then:

```bash
aws s3 ls "s3://<artifacts-bucket>/execs/$SANDBOX/"
```

**Expect:** a final object with a timestamp at or after the destroy call. EC2
sends an ACPI shutdown and waits before forcing power-off, which is what gives
`ExecStopPost` a window to run while the network is still up.

**If this step fails** — no final object lands — say so here plainly rather
than treating Step 4/5's manual-save success as sufficient. `docs/exec-capture.md`
promises that a graceful stop (including a terminate) saves the trace; that
promise has to hold here or be corrected in the doc, not asserted on the

## Step 10 — BPF coexistence: enforcer, exec tracer, and (optionally) the Wiz sensor

On a fresh `ebpf`/`both`-enforcement box:

```bash
systemctl is-active km-ebpf-enforcer km-execlog
```

**Expect:** both report `active`.

Confirm enforcement itself still works with the tracer also loaded. **Run this
as the sandbox user with a login shell, not as root** — Step 1's `km shell
--root` is for reading the exec store, but a probe run as root bypasses both
the uid-0 iptables RETURN and the sandbox cgroup, so an allowed-host connect
would pass trivially and `evil.example.com` would only fail because the on-box
resolver NXDOMAINs for root too — DNS doing the work, not the enforcement path
this step exists to prove is unharmed by the new tracepoints. `sudo -u
sandbox` alone is not enough either: it skips the profile that sets
`HTTPS_PROXY`, so the request egresses direct and gives a false negative
(the tell is HTTP/2 on the response — that means you bypassed the proxy and
this result cannot be trusted). Use `sudo -iu` for a real login shell:

```bash
sudo -iu sandbox bash -lc 'curl -sS -o /dev/null -w "%{http_code} %{http_version}\n" https://<a host on the allowlist>/'
sudo -iu sandbox bash -lc 'curl -sS https://evil.example.com/ ; echo "exit=$?"'
```

**Expect:** the allowed host connects (and reports **not** HTTP/2 — HTTP/2
means the proxy was bypassed); `evil.example.com` is blocked (times out or is
refused, per the profile's enforcement mode).

This is the load-bearing check of the step: km now loads cgroup BPF programs,
SSL uprobes, **and** four exec/exit tracepoints on one kernel. That
combination has never been run before this UAT. If a box also extends
`base/security/wiz`, repeat this check there too — the sensor adds its own
kprobes, and this phase's own design doc calls that the single most likely
place for an interaction nobody has seen yet.

- [ ] `km-ebpf-enforcer` active
- [ ] `km-execlog` active
- [ ] Allowed host connects
- [ ] `evil.example.com` blocked
- [ ] (if tested) same four checks pass on a `base/security/wiz`-extending box
